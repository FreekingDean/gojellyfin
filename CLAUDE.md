# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Go reimplementation of a Jellyfin media server, serving the Jellyfin 12.0.0 HTTP API so that stock `jellyfin-web` and Jellyfin clients can talk to it.

## Rules

**Comments.** Don't write them, and there is no exception. A comment is almost always a sign the code is messy or doing too much — simplify the code instead of explaining it. Where an external constraint genuinely cannot live in a name, it goes in the External constraints section below rather than beside the code. `//go:` directives, `//nolint` and generated headers are not comments and stay. `TestNoComments` in `cmd/gojellyfin` parses every file under `cmd` and `internal` and fails on anything else, so the rule is the build's rather than a reviewer's; a generated file is skipped by its own `DO NOT EDIT.` header.

**Paradigms.** Use what the codebase already does. Don't introduce a new pattern or a new dependency if the existing ones can carry the change, and never refactor toward a better paradigm mid-change. If something genuinely needs rework, open a GitHub issue with `gh issue create` and move on. Deferred work is tracked in issues only — there is no TODO file. Write the issue for someone reading it in six months: the concrete detail and the file or symbol it concerns, not a one-line reminder. Decisions get filed the same way, worded as the standing decision and its reason so nobody re-litigates them.

**Pull requests.** Never commit to `main`. Every change goes on a branch and lands through a PR for review, including one-line fixes and documentation. Push the branch and open the PR with `gh pr create` as soon as the work builds and boots.

**Worktrees.** Work happens in a worktree under `.worktrees/`, never in the main checkout — several branches are usually in flight at once. Create one with `git worktree add -b <branch> .worktrees/<name> origin/main`. The main checkout is reserved for tracking `origin/main`; don't develop or commit there.

**Commits.** Always be committing — don't wait to be asked, and never leave finished work sitting in the working tree. Commit as soon as a change builds and boots, then keep going. Small and iterative: each commit stands on its own and can be applied or replayed without depending on a later commit to make it valid. Migrations in particular must be safe to re-run.

## Commands

```sh
make dev                             # migrate, build and serve, with CORS open
make temporal                        # local Temporal dev server (brew install temporal)
make worker                          # background worker, dialing that server
make run                             # run once, no watching
make build test fmt
make lint                            # gofmt, go vet, golangci-lint
make generate                        # regenerate the API from the spec and the store from the ent schema
go test -run TestName ./internal/... # single test

echo hunter2 | go run ./cmd/gojellyfin adduser Dean   # bootstrap the first user
```

Everything ships as one cobra binary, `cmd/gojellyfin`, with a subcommand each for `server`, `worker`, `migrate`, `adduser`, `resetpassword` and `localizationdata`. One binary means one image, so an operator task is `docker exec <container> gojellyfin adduser Dean` rather than a second image or a second build. The names stay flat and read as commands; a new task is a `<name>Command() *cobra.Command` constructor in a file of its own, added to the list in `main.go`.

Three things are shared between them, all in `main.go`: `withStore` opens the store, starts it and closes it around a callback, `readPassword` reads from stdin, and the root command's `PersistentPreRun` logs `system.Build()` — cobra runs it only for a subcommand that has work to do, so `--help` stays quiet while every deployed run says which build it is. The DSN does not live there — `internal/env` is the single source, which is why `migrate` can name the same database the server will use without repeating the string.

`make dev` and `make run` tee to `/tmp/gojellyfin.log`, so the log is on screen and readable by tooling at the same time.

`build` depends on `generate`, and `run`, `dev` and `test` depend on `build`, so the generated code is never stale. `dev` migrates first and opens `CORS_ORIGINS`, which is what a browser served from somewhere other than this port needs; `run` does neither.

`make lint` is `gofmt`, `go vet` and the `golangci-lint` version `.github/workflows/ci.yml` pins. `.golangci.yml` enables the standard set plus the linters the tree already passes clean, so a green run means zero issues rather than a tolerated backlog. `funlen`, `gocyclo`, `revive`, `wrapcheck` and `paralleltest` are deliberately out because each has one — 53 functions over `funlen`'s default, 47 of them tests — and enabling a rule alongside exclusions wide enough to pass it leaves a rule nobody is held to. Those backlogs are #612's.

There is no watcher: `make dev` builds and runs once, so a change means restarting it. It `tee`s to `/tmp/gojellyfin.log`, so the log is on screen and readable by tooling at the same time; the request log is the fastest way to find what a client actually calls.

A running server owns `:8081`, so starting a second alongside it fails with `ListenAndServe error: address already in use`. Find the listener with `lsof -ti:8081 -sTCP:LISTEN` — without `-sTCP:LISTEN` it also matches browsers connected to the port, and killing those results is not what you want.

Requires a reachable Postgres. `DATABASE_URL` is required and the binary carries no default — a process that was not told which database to open fails at start rather than quietly dialing localhost. The development DSN (`postgres://localhost:5432/gojellyfin_development?sslmode=disable`) lives in the `Makefile` as a `?=`, so `make run`, `make dev` and `make test` supply it while an explicit `DATABASE_URL` still wins. Running `go test ./...` or the binary directly, outside `make`, means setting it yourself.

**`internal/env` is the only package that reads the environment.** It loads once into a `Config` that fx provides and every other package takes as a value, so the knobs are found by reading one struct rather than by grepping for `os.Getenv`, and a package under test is handed a value instead of having to set a variable. A one-shot subcommand calls `env.Load()` itself, because it has no lifecycle to hang it off.

The reading is `viper`, bound to the environment only — no config file, no flags, no watching. The `mapstructure` tag on each field is the variable's name, and `keys` walks `Config` to bind them, because `Unmarshal` only populates keys viper already knows about and `AutomaticEnv` does not register any. So a new variable is a new field and nothing else; `TestKeysCoverEveryVariable` names the whole set, which is where a rename shows up, and `TestEnvIsTheOnlyReaderOfTheEnvironment` fails on an `os.Getenv` or a `viper` import anywhere else.

A malformed value is refused at start rather than ignored. `TRANSCODER_JOBS=lots` used to fall through to the core count and `TRANSCODER_STALL_TIMEOUT=30` to thirty seconds, so a typo in a manifest became a capacity problem with nothing to point at.

`DATABASE_MAX_CONNS` (20) and `DATABASE_CONN_MAX_LIFETIME` (30m) size each process's pool, applied in the `fx.tmpl` behind `store.NewStore`. `database/sql` otherwise opens a connection per concurrent query with no ceiling and keeps two idle, so every replica could take as many of Postgres' `max_connections` as it had requests in flight and churn the rest. Idle connections are kept up to the same ceiling, because a pool that closes what it just opened pays the handshake again on the next burst, and the lifetime is what lets a Postgres or pgbouncer restart drain rather than wedge. The figures are a starting point with no measurement behind them; the variables are there so an operator sizes replicas times the ceiling against the server.

`HTTP_PORT` is what the server listens on and defaults to 8081, which is the port the `Dockerfile` and the chart in `charts/gojellyfin` already name — the variable exists so a second process can be brought up beside them, not to move the default.

`serverModules` and `workerModules` in `cmd/gojellyfin` both list `env.Module`, and `TestWorkerModules` guards the second the way `TestServerModules` guards the first — a command that composes its graph inline has nothing to validate, so the worker starting without a config it needs is only found by running it.

**A domain may be mocked; the database never is.** A consumer of a domain declares the interface it uses (`activitylog.ActivitiesService`), `mockgen` writes it to `mocks/` through a `go:generate` line beside it, and the test is a table of input, expected call and canned answer. A domain's own tests run against the real store, because what a query does to the database is exactly what they exist to prove.

`make test` needs one too — `internal/items` seeds real rows through `store.NewStore()` and fails rather than skipping when the database is unreachable, so a green run means the queries actually ran. Each test owns a library row and deletes it and its items on cleanup; point `DATABASE_URL` at a scratch database to keep development data out of it. CI runs the suite against a `postgres:16` service with `internal/store/migrations` applied by `atlas migrate apply`.

`make e2e` is the one test that boots the server, and it does so under the real `jellyfin-web` 12.4 client driven by Playwright — the same client the chart ships by default, so the suite tests what is deployed. Everything lives in `e2e/`. `setup/boot.js` builds the binary and `e2e/fixtures`, creates a scratch database on `DATABASE_URL`'s server and drops it on the way out, runs `migrate` and `adduser`, seeds two libraries, a series and a playable title, starts `server` on a port it got by binding `:0` — so it can never take `:8081` from a running server — and fronts it with `setup/proxy.js`, which serves the client from disk under `/web` and everything else from the API on one origin, the way the chart's route does, including sending `/web/ConfigurationPage(s)` back to the API. `.github/workflows/e2e.yml` runs it beside the unit tests; it needs Postgres, the atlas CLI, ffmpeg and Docker, and a red run fails the PR.

`jellyfin-web` is not published anywhere a test can fetch it directly — no npm package, no built assets on its releases — so `boot.js` copies it out of the `jellyfin/jellyfin:12.4` image into `e2e/.client` once, and CI caches that directory. `JELLYFIN_WEB` points at an unpacked copy instead.

**Screenshots are compared only in the pinned browser.** `npm run visual` (what `make e2e` and CI run) starts the `mcr.microsoft.com/playwright` image whose tag is the installed `@playwright/test` version, runs `run-server` out of the checkout's own `node_modules` inside it, and points the tests at it; `exposeNetwork: '<loopback>'` tunnels the browser's requests for `127.0.0.1` back to the harness, so nothing else changes. That is what makes a laptop and CI render the same fonts, and it is why the baselines in `e2e/tests/__screenshots__` carry no platform suffix. `npm test` (`make e2e-local`) uses a browser on the machine and sets `ignoreSnapshots`, so it checks behaviour and skips the pixels. `e2e/screenshot.css` is applied while a screenshot is taken: `jellyfin-web` picks a card's placeholder colour from its id and every run seeds fresh ids, so the shades are flattened there rather than masked per test.

**A pull request shows its screenshots.** After the suite runs, `e2e/setup/gallery.js` reads `.build/results.json` (the JSON reporter, on in CI only) and collects every screenshot as the commit rendered it, plus the baseline, actual and diff of each one that changed, and the `gallery` job renders the `index.html` and the comment body from that. The `publish` job in `e2e.yml` puts that and the HTML report on `gh-pages` under `pr-<number>/<head sha>/`, replacing the PR's previous directory, and keeps one comment on the PR, found by its `<!-- e2e-screenshots -->` marker, edited in place on every push. `gh-pages` is a single orphan commit rewritten on each publish, so it never grows history, and `e2e-pages-cleanup.yml` deletes a PR's directory when the PR closes. A fork's token cannot write, so only branches of this repository publish. The job is `continue-on-error`: Pages being down never fails a PR. `main` keeps a gallery of its own at `main/`, which no PR's cleanup touches: the `main-gallery` job runs after every run on `main`, replaces only the suites that run collected (the browser on a push, the emulators on the nightly schedule or a dispatch), stamps each suite's summary with the commit and time it ran, and renders the page again over every suite present, so the TV section survives a push that never started an emulator. The README links it.

**Adding a spec** is a file in `e2e/tests` named `<thing>.spec.js` that imports `test`, `expect` and the helpers from `./fixtures` rather than from `@playwright/test`. The `signedIn` fixture hands over a page already on the home screen; `harness` is the seeded names and the base url, which come from `boot.js` and the fixture binary, so new seed data is a change to both. `view(page)` is the view on screen — the client keeps every view it has shown in the DOM, hidden, and two are briefly visible while one replaces the other, which is why `open` waits until only one is — `openDashboard(page)` reaches the dashboard through the app bar's user menu, since 12 draws its own app bar on a desktop-sized window with no side drawer, and `card(page, name)` and `open(page, name)` find and open a card by its title, clicking the poster's corner because its centre is a play button. Navigate through the UI or with `page.goto(harness.baseUrl + '/web/#/…')`. A visual check is `await expect(page).toHaveScreenshot('<name>.png')` once the page has settled; the first `make e2e-update` writes the baseline, which is committed with the spec. A deliberate visual change is accepted the same way, or by committing the actual images from the `playwright-report` artifact a failed CI run uploads. The client routes on the hash, so `toHaveURL(/details/)` is how a test waits for a navigation; a failed test attaches the server log, a trace and a screenshot. The seeded playable title is VP9 and Opus in WebM, which every Chromium decodes. `transcode.spec.js` seeds an MPEG-4 Part 2 file no browser decodes, so playing it proves the server encoded it, and it plays the H.264 and AAC that comes back, which the pinned image's Chromium decodes and a Playwright Chromium on the host may not — so under `make e2e-local` that spec can fail for the browser rather than the server. Artwork is real: the seed paints a flat-colour PNG per title into `.build/posters`, the proxy serves it under `/fixture-posters` on the same origin, and the image row points there, which is what lets `collage.spec.js` read the library cards' collages back pixel by pixel. Single sign-on is on for every run: `fixtures oidc` serves the same mock provider `internal/sso/ssotest` gives the Go tests, auto-approving `harness.ssoUsername`, and `boot.js` points `OIDC_ISSUER_URL` at it, which is why the login page carries the SSO button and a password sign-in clicks `Sign In` by name. The page fixture refuses every origin but the client's, so a spec that follows the provider's redirect routes `harness.issuer` back through, as `oidc.spec.js` does. The seed also leaves the `smoke` user part way through `Fixture Alpha`, `Fixture Beta` and `Fixture Pilot`, with a backdrop on Beta and on the series and none on Alpha, so the home screen carries a Continue Watching row whose three cards are the poster, the item's backdrop and the series' backdrop; `continue-watching.spec.js` holds each rung.

**The native clients are driven on an emulator, and only when asked.** `make e2e-androidtv` (`npm run androidtv`) runs the release `jellyfin-androidtv` named in `e2e/clients/androidtv/app.js` on whatever `adb devices` lists, against the same harness: `clients/androidtv/setup.js` boots it, forwards the device's `127.0.0.1` to it with `adb reverse` so the app is given the address the server publishes, and installs the APK from the project's GitHub release into `e2e/.clients`. Playwright is only the runner (`androidtv.config.js`); there is no browser. `clients/adb.js` is the whole driver — what `uiautomator dump` says is on screen, a tap, a remote key, a screenshot — and it knows nothing about the app; the app's screens and view ids are in `clients/androidtv/fixtures.js`. A native app has no page to evaluate script in, so what it did is read back from the API as a second device (`clients/api.js`): a playback position is the `UserData` the app's progress reports wrote. Its screenshots are attached as `<name>-current.png` and published, never compared, because an emulator's frame carries a clock and is not reproducible the way the pinned browser image is; the QR on the sign-in screen is decoded from one with `jsqr`, the way a phone's camera would read it. The fixture is 180 seconds there rather than 20, so a thirty second skip lands inside it. In `e2e.yml` the `androidtv` job runs nightly on `main`, on `workflow_dispatch`, and on a pull request carrying the `e2e-clients` label, on a KVM-accelerated `android-tv` emulator; each suite's job runs `gallery.js collect` and the `gallery` job runs `gallery.js render` over all of them, so the page and the comment carry a section per client.

Nothing migrates at startup. Schema changes mean editing `internal/store/entities`, running `make generate`, then generating and applying the SQL by hand from `internal/store` (`atlas migrate diff` is not a `go:generate` line in `generate.go` because it needs Docker):

```sh
atlas migrate diff <name> --dir "file://migrations" --to "ent://entities" --dev-url "docker://postgres/16/dev?search_path=public"
atlas migrate apply --dir "file://migrations" --url "$DATABASE_URL"
```

`gojellyfin migrate` is the deployed spelling of that second line. It drives the `atlas` CLI rather than the Go SDK because the revision tracker that owns `atlas_schema_revisions` is not in the `ariga.io/atlas` module — it lives in the CLI repo under `cmd/atlas/internal/migrate/ent`, which nothing outside that repo can import. The migration directory is embedded through `internal/store/migrations`, so a deployed binary cannot drift from the schema it expects, and `atlas.sum` is still verified on every run.

The `Dockerfile` carries that one binary and the `atlas` binary, runs as a non-root user, and is built and pushed to `ghcr.io/freekingdean/gojellyfin` by `.github/workflows/docker.yml`. `CMD` is `server`, so the image serves by default and any other subcommand is a `docker run` argument — a worker is the same image run as `worker`, which is the whole reason background work is a workflow rather than a goroutine in the server. `entrypoint.sh` survives the consolidation for one reason: it migrates first when `MIGRATE_ON_START=true`. That has to stay outside the binary, because it is deploy policy rather than server behaviour — unconditional migration on start is unsafe with rolling replicas, so the default is a one-off `docker run --rm <image> migrate`.

**Every merge to `main` is a release.** The build reads the highest `vX.Y.Z` tag, adds one to the patch, tags the image with that version alongside `latest` and the commit sha, and pushes that tag only after the image is pushed, so a failed build burns no version. The version is computed in the run rather than pushed first and built off the tag, because a tag pushed with `GITHUB_TOKEN` starts no workflow — building on the tag would need a PAT and a second run to publish what the first already built. `concurrency: docker-<ref>` serialises the runs on `main`, since two merges reading the same highest tag would derive the same version and the second `git push` would fail after its image was already published. Manually pushing a `v*` tag still builds and publishes through the `type=semver` patterns, which is the escape hatch for a minor or a major: the next merge patches on top of it.

`charts/gojellyfin` is how that image is deployed — the API, the streaming pods, the worker and the `jellyfin-web` nginx, all from the one tag, which is the release version. It holds no credential and owns no storage: `DATABASE_URL`, `TMDB_API_KEY` and `OIDC_CLIENT_SECRET` are `secretKeyRef`s into Secrets the operator creates, and the media is a volume source handed to `media.volume` rather than a claim the chart writes. `TRANSCODER_JOBS` follows the workload's cpu request rounded down, so the encode slots move with the cpu instead of being a second number to keep in step. `MIGRATE_ON_START` is not exposed at all; migration is a one-off run, or the `pre-install,pre-upgrade` hook Job that a release carrying a migration turns on. The release step packages the chart with `--version` and `--app-version` both set to the version it just derived and pushes it to `oci://ghcr.io/freekingdean/charts` after the image and before the git tag, so a published chart only ever names an image that exists and a failed push burns no version; a manually pushed `v*` tag publishes a chart of that version the same way. The `version` and `appVersion` in `Chart.yaml` are placeholders for an unreleased checkout and are never bumped by hand.

## Architecture

### Wiring: uber/fx

Every package under `internal/` exposes a `Module` in its own `fx.go`; `serverModules` in `cmd/gojellyfin/server.go` composes them into the one `fx.New(...).Run()` that the `server` subcommand is. fx wires the long-running commands, not the CLI — `adduser` and the rest build what they need by hand, because a one-shot task does not want a lifecycle. `server` and `worker` each compose their own graph. New packages follow the same shape: `New` constructor in the package, `fx.Provide`/`fx.Invoke` in `fx.go`, `fx.Lifecycle` hooks in a `run` function for anything with start/stop semantics (see `internal/http/fx.go`, `internal/store/fx.go`).

The command lists the domains one by one, but not the forty tag packages: `server.Module` aggregates those, so a tag module is named beside its thirty-nine siblings rather than in the composition root, and the command reads as the domains plus the API surface they are served through. Tag modules are named `server/<tag>` because five of them share a package name with a domain (`items`, `playlists`, `localization`, `displaypreferences`, `system`) and fx prints the module name in its graph and its errors.

A module aggregates another only where the second is part of the first's own edge, not as a shortcut past the command: `server.Module` takes the tag packages, and `http.Module` takes `mux` and `transcode` along with `middleware.NewAuth`, `socket.New` and `stream.New`, because those are the transport it owns. Each subcommand still composes its own list — a transcode pod is the `server` command too, so there is no smaller graph to compose — the split is in the routing.

A binding that exists only because the object graph would otherwise be cyclic goes in the `fx.go` of the package that supplies the dependency, not the one that consumes it: `libraries`, `sources`, `items` and `probe` each hand their jobs to the `jobs.Registry` from their own `register`, so what a package runs in the background is answered by reading its `fx.go`.

`TestServerModules` in `cmd/gojellyfin/server_test.go` runs `fx.ValidateApp` over `serverModules`. A forgotten `Module` compiles cleanly — nothing references one except the list it belongs to — so the build cannot catch it and the server dies on start instead. `ValidateApp` checks the graph without opening a database or binding a port; dropping `mediainfo.Module` fails it with `missing type: *mediainfo.Server`.

**It does not catch a module replaced by its own constructor**, and that is a different bug with the same shape. `workerModules` listed `fx.Provide(items.New, libraries.New)` rather than `items.Module` and `libraries.Module`: every type still resolved, so `ValidateApp` was happy, but the modules' `fx.Invoke(register)` never ran and three of the six jobs were missing from the registry — the worker answered `unable to find activityType=RefreshLibraries` at run time. `TestCommandsComposeModulesRatherThanConstructors` parses `serverModules` and `workerModules` and fails on a `<pkg>.New` for any package that declares a `Module`, because the constructor is only ever the shorter way to say the same thing until the module grows an invoke.

### API layer: generated, with an unimplemented base

`internal/server/api` is entirely generated and should never be hand-edited. `go:generate` runs two steps:

1. `oapi-codegen` (strict server + models + embedded spec) → `jellyfinapi.gen.go`, a ~95k-line file defining `StrictServerInterface` with one method per Jellyfin endpoint.
2. `./gen` (a local AST tool) reads that interface and emits `unimplemented.gen.go` — an `Unimplemented` struct implementing every method with `ErrNotImplemented`.

`server.Server` embeds `api.Unimplemented`, so it satisfies the full interface while only the endpoints actually written exist as real methods. **Implementing an endpoint means adding a method to `internal/server` that shadows the embedded stub.** `ErrNotImplemented` is mapped to HTTP 501 by the response error handler in `internal/http/http.go`.

`spec/jellyfin-openapi-stable.json` is the vendored upstream spec and `spec/overrides.json` the `x-go-type` overrides `specpatch` applies to it where upstream types generate badly, so re-vendoring means replacing one file rather than re-applying patches by hand.

**Two versions, and they are different facts.** `system.JellyfinVersion` is the API this server speaks and `gen` writes it into `internal/system/jellyfinversion.gen.go` from the spec's `info.version`, because a second copy maintained by hand is how it came to claim 10.10.0 while the spec said 12.0.0. `internal/system` may not import `api`, which is why the generator writes across rather than the domain reading `GetSwagger()`. `system.Build()` is the other fact — which build of gojellyfin is running — stamped by `-ldflags -X` from the `Makefile` and the `Dockerfile`, defaulting to `dev` for a plain `go build` since `.dockerignore` drops `.git`. It reaches clients as `SystemInfo.PackageName`, not as `Version`: `jellyfin-web` refuses a server whose `Version` is below the `@jellyfin/sdk` minimum of `10.9.0` (`ServerUpdateNeeded`) and its discovery scores a `ProductName` other than `Jellyfin Server` as unusable, so neither field is ours to spend. Every subcommand logs `Build()` before it runs.

**The dashboard's Server version is the one place the build shows, and only `/System/Info` carries it.** `jellyfin-web`'s server panel renders `SystemInfo.Version` and nothing else from the server — Web version and Build version are constants compiled into the client — so `GetSystemInfo` answers `DetailedVersion()`, the API version with the build as semver build metadata (`12.0.0+gojellyfin.0.0.15`), which leaves precedence alone. `GetPublicSystemInfo` keeps the bare `Version()`, because that is the response every client gates on: the Kotlin SDK's `ServerVersion.fromString` behind Android and Android TV accepts only three or four dotted integers and answers null for anything else, and `jellyfin-web`, Swiftfin and Kodi all read their version off the public endpoint too. No client surveyed parses the authenticated one, and `jellyfin-web`'s own `compareVersions` would still read the metadata form as 12.0.0 if it did. The Makefile strips `git describe`'s leading `v` so a local build stamps the same form as the image's tag.

### Request path

`internal/http` owns the `net/http` server and composes two middleware layers: `middleware.HttpMiddleware` (stdlib handler wrappers — CORS, logging) applied outside, and `api.StrictMiddlewareFunc` (operation-aware, has the operation ID) applied inside the generated handler.

Routing uses a hand-rolled `internal/http/mux`, not `http.ServeMux`, because Jellyfin clients hit case-insensitive paths and paths with literal dots (`stream.mp4`). Patterns compile to regexes: `{name}` captures a segment, `*` is a catch-all, matching is case-insensitive, and a trailing slash is always tolerated. Path params land via `r.SetPathValue`.

`GET /socket` is registered outside the generated API for the websocket keepalive loop (`internal/server/socket`).

`GET /link` and `GET /link/{code}` are too (`internal/server/link`). A stock TV app shows a six-digit Quick Connect code and cannot draw a QR, so the TV's user types this server's address plus `/link` on a phone, and the redirect lands them on `jellyfin-web`'s own Quick Connect page with the code filled in. It is a redirect rather than a page of our own because that page already does the whole job: it asks for a login first and comes back, and it authorizes the code as whoever signed in. The chart needs no rule for it, since everything outside `/web`, `/Videos` and `/Audio` already reaches the API.

**The TV shows a QR for it, and the QR names the television rather than the code.** `link.Handler` owns three more things, all off unless `PUBLISHED_SERVER_URL` is set, because a QR has to carry an absolute address and one guessed from `Host` is one an attacker picks. `GET /link/qr.svg` draws the code; `branding` appends `link.CSS()` to `/Branding/Css`, which hangs that picture and the typed address under the code in `jellyfin-web`'s Quick Connect dialog; and `GET /Branding/Splashscreen` is the same QR on a 1920x1080 PNG for a native app that draws no CSS. What the QR encodes is `/link/tv/<16 hex of sha256(DeviceId)>`, and `link.FromDevice` resolves that at scan time to the newest code `quickconnect.Waiting` holds for the device. It cannot encode the code itself: a browser keeps a CSS background in memory, so a second Quick Connect in one page load redraws the first picture, and a native app caches its splashscreen long before it has asked for a code. A device is stable across both. `InitiateQuickConnect` tells the browser which device it is with a `gojellyfin_quickconnect` cookie scoped to `/link/qr.svg`, since an image request carries no `Authorization` header; the splashscreen reads `DeviceId` off that header when a client sends one. With neither, the QR is the bare `/link`, and `/link` finds the code itself when it can: `quickconnect.Nearby` answers the waiting requests started from the phone's network — the same address for public IPv4, the same /24 for a private one, the same /64 for IPv6 — and when every one of them is the same device name and app, which is one television asking more than once, the redirect carries the newest code. Two televisions waiting on one network, or none, is the empty field and the phone types the code. Only a network is enough because the phone still signs in and still presses Authorize, and what an unauthenticated visitor learns is a code the television is already showing to the room. That is what makes the Android TV app's QR scan-and-tap: it caches the splashscreen on disk under its url (Coil's default `CacheStrategy` ignores `Cache-Control`) and sends no `Authorization` with it, so the picture can never name the television. `link.spec.js` drives the whole loop: a second browser context is the television, the phone opens what its QR names, and the television lands on home.

So are routes Jellyfin serves but hides from its own OpenAPI document with `[ApiExplorerSettings(IgnoreApi = true)]`. There are 36 of them, almost all the pre-10.9 `/Users/{userId}/…` spellings, and no version of the spec contains any of them — searching a newer spec will not find them either. `spec/jellyfin-hidden-routes-10.10.0.txt` is the extracted list, and `TestLegacyRoutes` fails if one of them has neither an alias nor a stated reason. It is still the 10.10.0 extraction while the spec is 12.0.0, and the two have drifted (#589). `jellyfin-web` still calls some, so the symptom is a 404 for a path the spec does not define; the definition is in the controller source (`GET /Users/{userId}/Items/{itemId}` is `Jellyfin.Api/Controllers/UserLibraryController.cs`).

`legacyRoutes` in `internal/http/http.go` maps each to its documented spelling and re-dispatches through the mux, so an alias costs a table entry rather than a handler. `[Obsolete]` alone does **not** mean missing — most obsolete routes are still documented and already generated; only `IgnoreApi` hides them.

They register after the generated routes so a documented literal wins any overlap, and most-specific first: the mux matches in registration order with no notion of specificity, so `/Users/{userId}/Items/{itemId}` registered before `/Users/{userId}/Items/Resume` swallows it and passes "Resume" as an item id. `legacyPatterns` sorts by literal segments to keep that from depending on map order.

### External constraints

Code carries no comments, so the third-party behaviour it is written around is written down here instead. Each of these cost time to find once and would cost it again.

**Clients.** Jellyfin clients send query parameters in PascalCase while the spec declares them camelCase, and send `Param=` with an empty value where a value is undefined, which fails to parse as an int or a uuid and answers 400; `middleware.HttpCanonicalQuery` maps the case back and drops the empty, and `queryparams.gen.go` is the table it maps against. They also send an array either as repeated keys or joined with commas, which is how `jellyfin-apiclient` writes one and what upstream's comma-delimited binder reads, while the generated binder reads only the first; so the middleware splits a comma-joined value into repeated keys for the names in `CommaDelimitedQueryParameters`. `gen` lists a name there only when every operation declaring it declares an array and one of them types the items as something a comma cannot occur in (a uuid, a number or an enum), so `IncludeItemTypes=Movie,Series` splits while `SearchTerm`, `Genres` and `Studios`, which upstream pipe-delimits because a name can hold a comma, and `SortBy`, which two operations declare as a single value, are left whole. Media URLs, websocket handshakes and HLS subtitle playlists cannot carry an `Authorization` header, so the token rides in the query — `jellyfin-web` sends `ApiKey` and older Emby clients send `api_key`, and neither casing is canonicalised because those routes register outside the generated API. `jellyfin-web` 10.10 routes on the hash, so the Quick Connect page is `/web/#/quickconnect`, and it reads `?code=` into the field without submitting it. A signed-out visit is bounced to `#/login.html?url=<the route, encoded>` and both password and Quick Connect logins navigate back to `url`, which is what makes `/link` work on a phone that has never signed in. The page writes `code` into its markup through `dangerouslySetInnerHTML` without escaping it, so `/link` passes on the digits of what was typed and nothing else. An SSO sign-in cannot see that `url`, because the button is a static link in the sanitised login disclaimer and a fragment never reaches the server, so `/link` also sets `gojellyfin_sso_return` (the route, query-escaped, `Path=/sso/oidc`, ten minutes, `Secure`, `HttpOnly`, `SameSite=Lax`), which the OIDC callback reads to land back on `/web/#<route>` rather than on home. The Quick Connect prompt on the login page is a dialog with the id `quickConnectAlert`, whose text is `.dialogContentInner .text`; `/Branding/Css` is linked as a stylesheet, so a relative `url()` in it resolves against this server even in a client whose pages are not served from it. `jellyfin-web` 10.10 never draws `/Branding/Splashscreen` itself, so `SplashscreenEnabled` changes nothing in a browser. `jellyfin-web` 10.11 differs in three ways that each broke the QR on a deployed server while the suite, which runs 10.10, stayed green. It never requests `/Branding/Css`: it writes `CustomCss` from `/Branding/Configuration` into a `<style>` element, so `GetBrandingOptions` answers the same stylesheet `/Branding/Css` does and a rule that reaches only one of them reaches only one client version. It does draw the splashscreen, as the login page's backdrop in a `.backdropImage` whose `data-url` names `/Branding/Splashscreen`, cropped to cover the window — and that request carries no `Authorization`, so the picture meant for a native app names no television; `link.CSS` hides that element, which leaves the splashscreen to the clients that load no CSS. And its login route is `#/login?url=…` and its home `#/home`, with no `.html`, which is why `link.spec.js` matches `#/login` and `#/home` and passes against both. The native Android TV app does: it reads `SplashscreenEnabled` off `/Branding/Configuration`, refreshed at most every ten minutes, and draws the splashscreen full screen behind its user login screen, centre-cropped and under a dark tint, unless the user has turned backdrops off. It renders `LoginDisclaimer` through Markwon with the html plugin and no image plugin, so an `<img>` there draws nothing, it reads no `CustomCss`, and its Quick Connect screen is the code and its own strings. The Android TV suite has seen it on the emulator: the QR survives the tint and decodes and names the bare `/link`, because the app fetches the picture without the `Authorization` header that would say which device it is, and the redirect finds the code by the phone's network instead. Clients percent-encode the `Authorization` header's values, so `Jellyfin%20Web` arrives verbatim. The websocket client treats an unanswered `KeepAlive` as a dead socket and reconnects, so the timeout is advertised as 60s and `ForceKeepAlive` is pushed at half that. Clients switch to `SystemInfo.LocalAddress` when they believe they are on the same network, so an address this server cannot confirm is worse than none: they stop talking to the address that reached them and never come back. `jellyfin-web` retries a playback error until the url refuses both stream copies, which is why `served` writes `SupportsDirectPlay` and `SupportsDirectStream` false for video even though nothing here reads them. `DisplayPreferencesId` is opaque: the only value `jellyfin-web` sends is the literal `usersettings`, and the body it posts back is the object the GET handed it, so the `Id` inside it is our own value coming home and the id is read from the path. It is stored as sent, in `reference_id`, unique with the user and the client — the triple upstream keys on, so one user on two clients is two rows. Nothing precreates one: a `Get` that misses serves the schema defaults and writes nothing, because a precreated row freezes today's defaults and makes a choice the user made indistinguishable from one nobody ever set. `/web` is two prefixes at once: the one `jellyfin-web` is served under, and the one `/web/ConfigurationPage` and `/web/ConfigurationPages` live at — the only two spec paths beneath it. `jellyfin-web` calls the second on every dashboard load to build the admin left-nav, so a gateway that sends all of `/web` to the static client answers it out of nginx and 404s, and the plugin pages vanish with no error that names the cause. The chart's route carries an `Exact` rule for each of the four spellings the client uses (`ConfigurationPage`, `ConfigurationPages` and both lower-cased) back to the API — a case-insensitive `RegularExpression` rule was tried and did not route on a real gateway, since regex support and its precedence are implementation-specific; Gateway API grants an exact match precedence over any prefix across all applicable routes, ahead of path length, route age and list order.

**The Kotlin SDK decodes strictly.** The native Android apps talk through `jellyfin-sdk-kotlin`, whose models are generated from the 10.11 spec with `kotlinx.serialization`: a property the spec marks non-nullable has no default, so a response that omits one fails to decode as a whole, and the app reports it as `Unable to connect to server` with nothing in the server's log, because the server answered 200. `jellyfin-web` reads the same responses as loose JSON and never notices. That is why `SessionInfoDto` writes `LastPlaybackCheckIn`, `SupportsMediaControl` and `HasCustomDeviceName`, a public `UserDto` writes `HasConfiguredEasyPassword`, and `MediaSourceInfo` and `MediaStream` write `ReadAtNativeFramerate`, `IgnoreDts`, `IgnoreIndex`, `GenPtsInput`, `HasSegments`, `IsHearingImpaired` and `IsTextSubtitleStream` even where the answer is a constant: without the first three no television can sign in at all. The generated Go types make every field a pointer with `omitempty`, so the compiler does not help; the Android TV suite is what finds the next one.

**The SSO button and the way back to Quick Connect.** `jellyfin-web` renders `LoginDisclaimer` through `markdown-it` with html on and then `DOMPurify`, and rewrites every `<a>` in it to `target="_blank"`, so the button is a `<form action="/sso/oidc/start">` rather than a link — a link would sign in a new tab and leave the login page standing. `branding.GetBrandingOptions` appends it when sign-on is on; the stored disclaimer the dashboard edits is untouched, so saving branding never persists the button. Being sanitized it carries no script, so it cannot read the login page's `#…?url=` fragment, and a fragment reaches neither the server nor a `Referer`. The route a sign-in returns to therefore arrives as a cookie: the `/link` page sets `gojellyfin_sso_return` to `url.QueryEscape` of a `jellyfin-web` hash route such as `/quickconnect?code=123456`, on `Path=/sso/oidc` for ten minutes, and `/sso/oidc/start` also takes it as `?redirect=`. The callback lands on `/web/#<route>` only for a value that starts with exactly one `/` and holds no control character, and clears the cookie either way.

**Casting.** `jellyfin-web`'s Chromecast plugin starts only when the signed-in user's `Configuration.CastReceiverId` names a receiver, and its preferences page offers the ones `SystemInfo.CastReceiverApplications` lists, so an empty id hides the cast button with nothing but a console warning. `config.CastReceivers` is upstream's two, `F007D354` Stable and `6F511C87` Unstable, served whatever the stored server configuration says because nothing can edit them, and `config.CastReceiverID` answers the stored choice only when it is one of them and the stable one otherwise, the rule upstream's `UserManager` applies. The receiver is a page on `https://apps.jellyfin.org/chromecast/`, handed the server address and the sender's token, and every API call it makes is cross-origin, so `newHTTPMiddleware` always allows that origin beside `CORS_ORIGINS`: with no CORS the television accepts the cast and then fails its first request. It plays the `TranscodingUrl` as `video/<TranscodingContainer>`, which is why that field has to match the url's suffix.

`jellyfin-web` 12 asks `/Items/{id}/Ancestors` and `/Items/{id}/Collections` on every detail page, a title the library lacks included, so the first answers the root folder alone for an id `discover.Parse` reads and the second answers an empty list, there being no collections; its Backups and Logs dashboard pages are answered with empty lists for the same reason.

**Postgres LISTEN/NOTIFY.** `pg_notify` refuses a payload over 8000 bytes, so `notify.Publish` refuses one over its own limit with an error rather than letting it vanish — a SyncPlay group is a handful of sessions, nowhere near it. Publishing goes through the store's pool, but `LISTEN` binds to a connection for as long as it is listening, so `internal/notify` holds one `pgx.Conn` of its own for it, and issues the `LISTEN` before `Start` returns, or an update published immediately after boot is lost to a listener that has not registered yet. Losing that connection is how a dropped listener is noticed; every notification in the gap before it reconnects is gone, which is why the reconnect logs how long it lasted. The one handler — `socket.Deliver`, bound in `internal/http/fx.go` — runs on the listener in order, because a group's updates only make sense in the order they happened, so a handler that blocks stalls delivery for every other one.

**Generated code.** `oapi-codegen` normalizes operation ids into Go method names, so the spec's `GetBrandingCss_2` becomes `GetBrandingCss2` and the middleware only ever sees the normalized form. It splits a JSON body across two fields depending on content type, which is what `apiutil.Body` folds back together. It types the vendored spec's free-form `DeviceProfile` as an opaque object, so `mediainfo` reads it back out of json rather than binding a generated type. It emits only the schemas an operation references, so the spec's `SyncPlayGroupUpdate` and its variants are pruned and `internal/server/syncplay` declares the shapes it pushes over the websocket itself. Body decoding and parameter binding both answer 400 from inside the generated wrapper, so the handlers in `internal/http/http.go` are the only place either reason is visible.

**Authorization.** Scopes come from the spec through `api.OperationPolicies`, so an operation is authorized by what upstream declares rather than by whether a handler remembered to check. An operation in neither that table nor `PublicOperations` is refused, and `users.Satisfies` refuses a scope it does not name even for an administrator, so a re-vendored spec that renames one fails loudly and closed rather than serving it unguarded.

**Path containment.** `filesystem.resolve` bounds a client-supplied path to `MEDIA_DIRECTORIES` with `filepath.Rel` and a `..` test rather than `strings.HasPrefix`, because a string prefix admits `/mediasecrets` under a root of `/media`. There is no stdlib helper for this — `filepath.HasPrefix` is documented as broken and https://github.com/golang/go/issues/18358 is why it was never fixed. `Rel` is used rather than appending a separator to the root because the default root is `/`, which would give `//`. It bounds the name the client sent; a symlink inside a root that points outside it is not followed up, so the roots are trusted to be trees the operator meant to publish. `sources.Localise` bounds what Sonarr and Radarr report to one of the source's `source_paths` the same way, because a reported `/movies/../etc/passwd` passes a prefix test and `filepath.Join` then cleans it out of `local_path`.

**ffmpeg and ffprobe.** `image.DecodeConfig` needs each format's decoder registered by blank import or every image reports 0x0. ffprobe reports muxer families like `matroska,webm`, so the file extension picks the one clients are told about, and some containers hang their tags off the media stream rather than the format, where the format wins a shared key. The ffprobe timeout is deliberately shorter than the heartbeat window a step is given: an abandoned step is never told to stop, and a read that has wedged has no loop to be told in. ffprobe's JSON writes every numeric as a string and omits a key it has no value for rather than writing `"N/A"`, so `,string` is safe on `bit_rate` and `sample_rate` but wrong on anything that is not an integer: `duration` is `"1.023000"` and `avg_frame_rate` is the rational `"30/1"`. `,string` is strict, so one `ParseInt` failure fails the whole decode and every file stops probing — which is why the fields are typed to what the store holds and `internal/ffmpeg` probes a real file rather than trusting the build. ffprobe missing is not a startup failure: `ffmpeg.New` records an empty path and `ProbeFile` answers `ErrNotAvailable`, which the scan reads as nothing to learn, so a box without it serves rather than refusing to build the graph — the same answer `internal/transcode` gives a missing ffmpeg.

**TMDB.** The image base url and the size segments are declared nowhere but `/configuration`, so nothing may hardcode `https://image.tmdb.org/t/p/`; the response is highly cacheable and the endpoint is the only new call artwork costs, because `poster_path`, `backdrop_path` and `still_path` already ride on the detail responses the identify job fetches. The images themselves come off a CDN rather than the API, so a download is outside the rate limiter and its own timeout is the only thing bounding it. Two facts about `golang-tmdb` shape the tests: `SetCustomBaseURL` writes a **package-level** variable rather than a field, so every client built in one process shares whatever the last call set, and `GetConfigurationAPI` builds its url off that same variable — which is what lets an `httptest.Server` answer `/configuration` at all. A counter in a stub that tallies every request rather than the path it cares about will now read one high, which is how `TestRetrying_RoundTrip` first noticed the extra call.

**Jellyfin's own database.** `scripts/jellyfinmigrate` reads it, and its fixtures in `migration/fixture` are the tables as Jellyfin's source declares them rather than a dump of a live install. `jellyfin.db` holds `Users`, `Permissions`, `Devices` and `ApiKeys`, the same in 10.10 and 10.11. A password is a PHC string with salt and hash in **hex**: `$PBKDF2-SHA512$iterations=<n>$<salt>$<hash>` is HMAC-SHA512 with a 64 byte key, legacy `$PBKDF2` is SHA1 with 32, and `auth.Verify` accepts both. `Permissions.Kind`, `SubtitleMode` and `SyncPlayAccess` are enum ordinals. EF Core writes a `Guid` as upper-case text and a `DateTime` as `yyyy-MM-dd HH:mm:ss.FFFFFFF` in UTC with no zone. `Devices.IsActive` is cleared on sign out and an active token never expires. Watch state is where the two versions part. 10.10 keeps it in `library.db`: `UserDatas` is keyed by a string and by `Users.InternalId`, an item's rows are written once under each of its user data keys — a provider id, or the series' key followed by the season as three digits and the episode as four — and once under its id with no dashes, `TypedBaseItems.UserDataKey` holds only the first, ids are 16 byte blobs in .NET's mixed-endian order, and `ProviderIds` is `Imdb=tt1|Tmdb=2`. 10.11 moved everything into `jellyfin.db`: `UserData` is keyed by `ItemId` and `UserId`, `BaseItems` replaces `TypedBaseItems`, and provider ids are rows in `BaseItemProviders`. The server's id is in neither: it is the contents of `device.txt` beside the databases, 32 hex characters.

**Postgres and ent.** The `library_id,key` unique index is deliberately not partial on `deleted_at`, because a title that comes back has to conflict with the row it left behind. External subtitle streams are indexed off the end of the container's own, so the source row is locked for the whole rewrite or two writers allocate the same index. Next-up needs `DISTINCT ON` to pick one row per series with the `ORDER BY` deciding which, which the query builder cannot express, so `items.NextUpEpisodes` is raw SQL. Postgres does not parameterise a database name, so the e2e fixture interpolates one it built itself. A `bytea` holding a JPEG or PNG is `SET STORAGE EXTERNAL`, because the bytes are already compressed and the default `EXTENDED` spends a pglz pass that cannot shrink them; reading one materialises the whole object in memory, which is fine for a poster and is the bound to state before anything larger is stored that way.

### Tracing

Every operation gets one span, named for its **operation id**. That is why the span sits on the `api.StrictMiddlewareFunc` layer rather than the stdlib one: only the inner layer is handed the operation id, and a span named for a route pattern or a raw path is much less useful. It is last in `apiMiddleware`, which the generated wrapper folds outermost, so it measures authentication and authorization too.

`OTEL_EXPORTER_OTLP_ENDPOINT` is the only spelling read. The OTLP specification also defines a signal-specific `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, and supporting both would mean carrying its precedence rule and its different path semantics for a second way to say the same thing; one prescribed variable is the standing decision. Unset means tracing is off: no provider, a noop tracer, nothing dialed, and `tracing.Enabled` false, which is what keeps the span middleware out of the stack entirely rather than wrapping every request in a tracer that discards it.

The endpoint is checked in `tracing.New` rather than in `env.validate`, because what makes an OTLP endpoint valid is the exporter's business and `env` only knows it wants a string. The exporter answers a URL it cannot parse by logging and carrying on against its own localhost default, so a malformed one is refused at start instead.

**`internal/observability/tracing` is the only package that imports otel.** A caller gets `StartRequest` and a `Span` with `End` and `Fail`, not a `trace.Tracer`, so the middleware names no otel type and the backend stays swappable; `Recorded` is the same seam for tests, handing back a `Recorder` that answers in span names and attribute values; `TestOtelStaysBehindTracing` fails on an otel import from anywhere else. It is composed through `observability.Module`, which `server` and `worker` both list, and it registers `OnStop` only — a provider is exporting from the moment it is built, so there is nothing to start. The flush is bounded on the way out, because a collector that has gone away must not hold the process open.

**Streaming endpoints are excluded.** `streams` in `internal/http/middleware/oapitracing.go` names `Videos` and `Audio`, the same two roots the chart's `httproute.yaml` splits on, matched case-insensitively because the mux is. A progressive response runs for the length of the media, so a span covering one is open for hours — a leak rather than a trace. `GET /socket` needs no entry: it is registered outside the generated API, so it never reaches this layer. The streaming case in `TestOapiTracing_Middleware` is what keeps the exclusion from being incidental.

Nothing the client sent goes on a span. The query string carries `api_key` and some paths carry names, so only the method and the operation id are recorded; `TestOapiTracing_Middleware` holds that, because traces ship to third-party backends.

### Domain services

Three layers, split on what each is allowed to know:

- **`internal/{auth,sessions,users,items,libraries,tasks,config}` — domains.** Behaviour over the ent models, exposing a `Service` built with `New(client *store.Client)`. **A domain package must never import `internal/server/api` or `internal/http/middleware`.** That invariant is what the layout rests on, and `TestDomainsImportNoAPIOrMiddleware` in `internal/server/layering_test.go` is what holds it: it walks `cmd` and `internal` outside those two directories and fails naming the file and the import. `auth` owns hashing, tokens and request identity; `sessions` owns the active session and device rows, which are Jellyfin sessions rather than login state; `tasks` owns the workflows the dashboard drives.
- **`internal/server/<tag>` — one package per spec tag.** Named for the tag (`userlibrary`, `librarystructure`, `mediainfo`), holding exactly the operations that tag declares and a `Server` with the domain services it needs. Add a tag package by looking the operation up in the spec, not by guessing where it feels like it belongs — `AuthenticateUserByName` is a `User` operation, `GetBitrateTestBytes` is `MediaInfo`.
- **`internal/server/apiutil`** — five generic helpers (`Ptr`, `Deref`, `OrElse`, `Body`, `ZeroOrNilPtr`) and nothing else. It imports none of our packages, and no domain knowledge belongs in it; Go cannot alias generic functions, which is the only reason they are shared rather than copied.

**A tag package never imports another tag package.** Translation two or more tags need lives in **`internal/server/dto`** — `ItemDto`/`ItemDtos`/`LibraryView`/`UserItemDataDto`/`Kinds`/`SessionDto`/`CultureDtos`/`CountryInfos`/`ParentalRatings` today, in both directions, model→DTO and DTO→model. It may import `api`, `apiutil` and the domains, and it must never import a tag package. Domains cannot hold any of it, because they would have to import `api`.

Translation a single tag uses stays in that tag's `dto.go` and is **unexported** — `user.userDto`, `playlists.playlistDto`, `scheduledtasks.taskInfo`. That is what gives the rule its teeth: **no exported translation function in a tag package**, so there is nothing for a second tag to reach for, and the second caller is the moment a helper moves to `dto`. `Test` in `internal/server/translation_test.go` parses every tag package and fails on an exported function whose signature names an `api` type. Its exception table is the whole of the escape hatch: `configuration.ServerConfiguration`/`BrandingConfiguration` read stored config rather than translate. Adding a name there needs a reason, and a stale entry fails the test too.

**The alpha picker filters on `sort_name`, not `name`.** `NameStartsWith`, `NameStartsWithOrGreater` and `NameLessThan` are the three parameters behind the A-Z strip, and they are compared against `sort_name` because that is the column the list is ordered by — so the letter a title answers to is the letter it appears under. `sort_name` is stored lowercased with a leading article stripped, which is why the comparison lowercases what the client sent and why `The Matrix` is found under M and not under T. `#` reaches the server as `NameLessThan=A`, which is what puts `2001` before the letters.

Two naming traps, both of which cost real time: generated operation names occupy the method namespace, so domain queries need distinct names (`ItemByID`, not `GetItem`); and package names are easily shadowed by locals — `items []items.Item`, `dtos := make(...)`. Name the local something else.

`internal/server` itself is only the composition root plus the transport edge (`api`, `socket`, `stream`, `link`, `sso`). `link` is the one of those a tag package takes: `quickconnect`, `branding` and `image` each declare the one method they use, because the cookie, the stylesheet and the splashscreen are three faces of one QR.

Cross-domain wiring uses interfaces declared by the *consumer*, and where that would make the object graph cyclic the dependency is set after construction via `fx.Invoke` rather than in the constructor — see Wiring above for where those invokes live.

`server.Server` embeds each service, and embeds `api.Unimplemented` **one level deeper** through `nestedUnimplemented`. Go resolves a method at the shallowest depth where exactly one candidate exists, so a service at depth 1 wins and everything unimplemented falls through to the 501 stub at depth 2. Three things silently break this, all surfacing as a confusing "does not implement StrictServerInterface": a service embedding `api.Unimplemented` itself, two services declaring the same method, or flattening the wrapper. Embedded field names are type names, so each service is embedded through a local alias (`type UsersServer = users.Server`) to keep them distinct.

### Persistence

`internal/store` is generated by ent from the schemas in `internal/store/entities`, and should never be hand-edited — `fx.go` and `txhelper.go` look hand-written but come from `internal/store/templates`, so changes go in the template and get regenerated. There is no `Store` interface and no shared repository; domains hold a `*store.Client` and alias the models they own (`type Item = store.ItemModel`).

**A domain hands out a model, never an entity.** `model_exports.tmpl` generates a plain `<Node>Model` beside each entity: its fields, its foreign keys as ids, and its edges as models rather than an `Edges` struct. A query answers one through `SaveModel`, `OnlyModel`, `FirstModel`, `AllModels` or `GetModel`. A model carries no client, so nothing handed one can walk back into the database from it. An optional column whose zero would be a lie is `Nillable`, so an unprobed width is nil rather than 0; a string whose empty value already means absent is left alone.

**A write payload is the entity, not a copy of it.** `SaveScanned`, `SaveSource`, `SaveProbe`, `SaveImage`, `sessions.Create` and `activity.Record` each used to take a hand-written struct whose fields were a subset of the table's columns, so a new column meant editing the schema, the struct and the builder, and the two could disagree with nothing to say so. They take the model now, and a nested collection rides on its edge — a probe is a `MediaSource` carrying `Streams`. What stays hand-written is a shape that is genuinely not the table: `items.Metadata` and `displaypreferences.Settings` are pointer-per-field partial updates feeding `SetNillableX`, `sources.Title` and `ffmpeg`'s probe model third-party payloads, and `items.Named` is `{ID, Name}` for three tables at once.

The trap is that the entity brings its own `ID` along. `library_sources` carries the binding's id and the library's, both `uuid.UUID`, so a literal that said `ID:` where it meant `LibraryID:` compiles and points at the wrong row; the two places that read a binding's library were the whole of that surface, and grep is what finds them.

Domains never expose an ent type through a name the api layer has to know. They alias the model and its enums (`items.Kind`, `libraries.CollectionType`) so tag packages can build DTOs without importing `store`.

Edges that queries and DTOs read constantly declare their foreign key as a field (`edge.From("library", …).Field("library_id")` alongside `field.UUID("library_id", …)`). Without it ent keeps the column unexported, every read of a parent id costs an eager load, and upserts have no conflict target to name.

Anything a create has to supply on every call belongs in the schema as `.Default(...)` rather than in the caller — that is what keeps the ~40-field `UserPolicy` and `LibraryOptions` rows constructible from the domain, which cannot see the api defaults. Update paths take the opposite shape: ent generates `SetNillableX` for every field, which is exactly the pointer shape the api sends, so tag packages chain those onto a builder the domain hands back.

Ent's default delete action is `NO ACTION` for a required edge and `SET NULL` for an optional one, so a child row either blocks its parent's delete or is left orphaned with a dangling column. Owned rows carry `.Annotations(cascadeOnDelete)`, which only takes effect on the `edge.To` side — ent skips the inverse edge when it builds the foreign key, so on the self-referencing `children`/`parent` edge the annotation goes before `.From("parent")`. Deleting a library therefore takes its items with it, and a user takes their sessions and watch state; only activity log entries are left behind, keeping their history when the user or item goes away.

**An item is global. A library is a view of one.** `item` carries no `library_id` and its identity is `key` alone, so a film held by two libraries is one row with one watch state, one favourite and one search result rather than two that drift apart. Which libraries show it is `library_items`, written by the scan.

**The scan writes every file a source holds, and membership only for the tagged ones.** That split is what makes the two sweeps separable, and getting it wrong is destructive rather than untidy: with `Titles` filtering by tag before returning, a library's scan saw only its own subset, and the per-source file sweep then deleted every file the *other* libraries' subsets held. Two libraries fed by one instance alternated contents on every run and re-probed the survivors. `sources.Title` therefore carries `Tagged` rather than being filtered, and `TestScanLibrary_SharedSource` holds the line.

**That table is authoritative, not a cache.** Membership cannot be derived from `item_source → source → library_sources`, because a binding's `tag_filter` is applied per title at fetch time and that decision is stored nowhere: one Radarr feeding a `4k` library and a `kids` library sends different subsets to each, so deriving through the source would put every title in both. It carries `source_id` as well for the same reason the sweep needs it — with two sources feeding one library, the `(library, source)` pass has to know which rows are its own.

**The sweep is a reference count.** A binding that stops matching a title drops its membership row; a title is soft-deleted only once no `item_source` anywhere reports a file for it, and a season or series once nothing living hangs beneath it. Losing a tag and losing a file are different events, and the split tells them apart — a title dropping out of one library no longer erases the watch state another library still has a copy for. `SweepUnreachable` runs once per scan rather than per library, because the count is global.

**An `Item` is a title; an `ItemSource` is a file.** The name is the join it is — this item, from that downloader — which is why `item_source.source_id` reads correctly and why `unique(item_id, source_id)` is the right constraint: Radarr reports one file per movie and Sonarr one per episode, so a title with two copies has them from two instances. It was `media_source`, after upstream's `MediaSourceInfo` DTO, which collided with `sources` meaning a Radarr; the DTO keeps upstream's name at the boundary and the table says what it holds.

 The item carries no path — its identity is `key`, unique, derived from the TMDB id the source reported (`movie:tmdb:603`, `series:tmdb:1396`, `season:tmdb:1396:1`, `episode:tmdb:1396:1:3`). Keying on location meant a moved file changed identity and a reorganised library lost every resume position and play count; a name-derived key survives the move, and Sonarr and Radarr moving a file is the ordinary case rather than the exception. The key is internal — no endpoint takes one in its path and the spec has no field to put one in, so clients only ever see the UUID. `ItemSource` owns the path, unique per library, and an item may have many, which is how a 4K and a 1080p rip of one film become one entry with two versions.

The key is the whole of the grouping: two files two sources report under the same title and year are two copies of one title, which is how a 4K Radarr and an HD Radarr bound to one library become one entry with two versions. Nothing reads the runtime to second-guess that, so the scan needs no ordering between probing a file and deciding which item it belongs to.

`probed_at` and `date_modified` live on the source, so an unchanged file costs no ffprobe.

**Merging duplicates is the migration's job, not the scan's.** Going global made two rows with one key a conflict, so the migration folds the copies other libraries held into the oldest: files, children, playlist entries and activity move over, and a user with data on both keeps whichever answer says the title was watched — played and favourite OR'd, count and position taking the further of the two. Afterwards nothing can produce a second row for a key, because `SaveScanned` upserts on it, so `items.Merge` and the legacy rekey it existed for are gone. A database still carrying pre-August path keys is refused by the migration with what to do, rather than silently gaining a sibling for every title.

An item with more than one source has to pick one, and which one is answered in three places by three different rules. `PlaybackInfo` asks `items.SourceFor`, which walks the files tallest first (see Transcoding). A stream url names its source id and the handler serves that file, because this server wrote the url. A download takes `items.BestSource`, ignoring compatibility entirely, because the bytes are being saved rather than decoded and what the far end can play is its own problem; it is also the fallback when a stream url names no source at all, which no url this server writes ever does.

**A credit is upserted, because a provider credits one person twice.** `credit` is unique on `(kind, role, item, person)` and a crew credit carries no role, so TMDB listing the same producer under two departments is two rows that collide — and the insert failed the whole `UpdateMetadata` transaction, so a film with a doubled crew credit got no metadata at all rather than one credit fewer. The clear before it stays: that is what drops someone who has left the cast, and the conflict target only ever fires on a duplicate inside one payload.

An upsert whose conflict does nothing returns **no row**, which ent surfaces as `sql.ErrNoRows` rather than as success, so a caller that wants first-write-wins has to read that as the conflict it is; `items.SaveImage` did not, and a rescan writing a poster already on the item failed the whole scan step until it did. Columns owned by a background process must be left out of an upsert's `DoUpdates` — the scan clobbering probe-owned columns like `run_time_ticks` was a real bug. `SaveScanned` writes the item's `date_modified` and `SaveSource` the source's; the probe writes `container`, `run_time_ticks`, `size`, `bitrate`, `probed_at`, `tags`, the source's streams and the genre, studio and credit edges, and rewrites all of them on every run, so the edges are cleared and re-added rather than merged.

**The scan owns a title only until something better does.** `name`, `sort_name` and `production_year` have three writers — the scan takes them from the source, `internal/metadata` writes what the provider answered, and the metadata editor writes what a user typed — so `SaveScanned` writes them through a `CASE` in its `DoUpdates` rather than unconditionally: the scanned values land only while the row carries no `provider_ids`, is not `lock_data`, and does not name `Name` in `locked_fields`. A title renamed in Sonarr or Radarr therefore still retitles an item nobody has claimed, and an identified or edited one stands. `index_number` and `parent_index_number` stay refresh-owned in every case, because they are what the key is built from and the source is what says which episode a file is. So `items.Metadata` carries neither and the editor's `IndexNumber`, `IndexNumberEnd` and `ParentIndexNumber` are dropped at the boundary like its `Path` and `Container`, rather than written for one scan and sending an identify run at the wrong episode in between. A user edit is a claim: `items.EditMetadata` adds `Name` to `locked_fields` when the request changes the name, the sort name or the year, which is the lock `internal/metadata` already honours through `stripLockedFields` — one mechanism, three writers, rather than a second ownership column beside every one it protects. `locked_fields` is nullable and `NULL @> anything` is `NULL`, so the containment test is wrapped in `COALESCE`; without it the predicate is never true and the scan stops writing titles at all, which is insert-only wearing a disguise.

The sweep is split the same way. Items are swept by key and **soft** deleted, because the row carries the id the watch state hangs off and a returning title has to land back on it; sources are swept by path and **hard** deleted, because nothing hangs off a source that a returning file would want back. Losing one of two copies therefore costs a source row and nothing else.

Ordering by a to-many edge makes ent group the query, so the sort column comes back unaggregated and Postgres rejects it. Query from the side that owns the column instead (see `items.ResumeItems`).

### Background work

Background work runs as Temporal workflows in a separate deployment. `gojellyfin worker` is the same image and the same binary as the server, run as a second deployment, and `TEMPORAL_HOSTPORT` is the server it dials. Both reach `internal/jobs` as `env.Config.Temporal` rather than through `os.Getenv`. With the address unset, background work is off and the server still starts — a developer running the server alone gets a server rather than a dial error.

`TEMPORAL_NAMESPACE` has no default, and `jobs.NewClient` refuses to build a client without one rather than `env` inventing it: a namespace is only required once there is a server to dial, and defaulting it silently puts every run in whichever namespace the constant happened to name. The check belongs with the client because that is what needs the value.

`internal/jobs` is the client, the worker and the registry the `ScheduledTasks` API is served from, and it is the only package that names the engine — `internal/jobs/abstraction_test.go` fails on a `go.temporal.io` import anywhere else. A package declares what it runs beside the code that implements it, and each registers its jobs in its own `fx.go`, so the worker command lists no workflows of its own.

**A job is a name and a `Run(ctx context.Context) error`, and nothing else.** No workflow context, no futures, no steps, no children. `Run` receives a plain context and does ordinary Go: loop, heartbeat, log what failed, carry on. Everything it needs arrives as parameters — `jobs.GetParam[T](ctx, name)` — and anything it wants to schedule goes out the same way, `jobs.Enqueue(ctx, name, jobs.With("library", id))`, which returns immediately and waits for nothing.

Underneath, one generic workflow executes one activity: the named job's `Run`. That is forced rather than chosen — workflow code has to be deterministic and replayable, so it can do no IO, and a `Run` that touches the database has to be the activity. Keeping the workflow to a single `ExecuteActivity` is what makes the whole of a job ordinary Go with no replay semantics to reason about.

**The workflow id is `<name>:<sha1 of the parameters>`**, so one title's `RefreshItem` and another's are separate singletons and an enqueue that arrives twice with the same parameters collides with the execution already running and answers success. It is a hash rather than the parameters themselves because `RefreshItem` carries a whole title in its params and Temporal caps a workflow id — spelling them out produced an id thousands of bytes long. The `:` matters: `jobs.executions` finds a task's runs with `WorkflowId = <name> OR WorkflowId STARTS_WITH <name>:`, so an id built with any other separator leaves every task reading Idle on the dashboard and makes Cancel a no-op. That is what makes fire-and-forget safe without any bookkeeping: a retried activity re-enqueues its children and starts nothing new.

Enqueued jobs are independent top-level executions, never children. A parent's history grows by about three events per child and a Temporal workflow is terminated somewhere around fifty thousand, so a parent that fans out to thousands is the one shape that does not scale; thousands of *independent* executions are what the engine is built for. The cost is that stopping a job stops only that job — cancelling a scan no longer reaches what it enqueued.

**Running background work locally is two terminals.** `make temporal` starts the CLI's dev server — in-memory, so a restart is a clean slate, with the web UI on `http://localhost:8233` — and `make worker` runs `gojellyfin worker` against it on `localhost:7233` in the `gojellyfin_development` namespace. The CLI is `brew install temporal` or `https://temporal.download/cli.sh`, and deliberately not `go install`: its `go.mod` carries replace directives, which `go install` refuses.

`TEMPORAL_HOSTPORT` is **not** exported by the Makefile, which is the whole point of it being a variable there. `jobs.NewClient` dials at construction, so a server told about a Temporal that is not running refuses to start, while one told nothing serves with background work off — the property that lets a developer run `make dev` alone. Giving the running server the `ScheduledTasks` API is opting in by hand: `TEMPORAL_HOSTPORT=localhost:7233 make dev`.

A job can be driven without the API at all, which is the fastest way to test a change to one:

```sh
temporal workflow start --namespace gojellyfin_development --task-queue gojellyfin \
  --type RefreshLibrary --workflow-id RefreshLibrary --input '{}'
temporal workflow describe --namespace gojellyfin_development --workflow-id RefreshLibrary
```

The type is the job's `Name` and the workflow id is the same string, because the task id is the workflow id.

**The task id is the workflow id.** That is what gives a task singleton semantics without a lock or a dedupe column — Temporal refuses a second execution under an id that is already running, so pressing Start twice, `RefreshLibrary` and a schedule all collapse into one run. It also means state is one `DescribeWorkflowExecution` on a known id rather than a search over history, which is why `internal/tasks` needs no visibility query and no stored mapping.

**The refresh is four jobs, each in the package that owns what it writes.** There is no scanner package: it was the `filepath.WalkDir` one, and when the walk became Sonarr and Radarr the name stopped describing anything while the probe stayed bolted to it.

```
RefreshLibraries       libraries  every library        -> RefreshLibrary per library      *
RefreshLibrary         libraries  one library          -> RefreshLibrarySource per binding
RefreshLibrarySource   sources    one (library,source) -> RefreshItem per title
RefreshItem            items      one title            -> ProbeFile per unprobed file
                                                       -> RefreshItemMetadata if unidentified
ProbeFile              probe      one file
ProbeFiles             probe      every unprobed file                                     *
RefreshItemMetadata    metadata   one item
RefreshMetadata        metadata   every unidentified or artless item                      *
SweepItems             items      the reference count                                     *
```

**One job does one thing, and `Startable` (marked `*`) says which a person may press Start on.** The four marked are what the dashboard lists and the only ones `jobs.Start` accepts; the rest are only ever enqueued by the level above, and starting one by hand would run it with no parameters. `Registry.All` is still what the worker registers as activities, so every job runs — the split is only in what is offered.

A batch and its leaf are two names rather than one job branching on whether a parameter is set. That is not tidiness: `jobs.executions` finds a task's runs with `WorkflowId = <name> OR WorkflowId STARTS_WITH <name>:`, so one name for both made the dashboard's Refresh Metadata row read Running whenever any of ten thousand per-item identifies was in flight, and made Cancel stop all of them.

**The names are in `internal/jobs`, not in the package that runs them.** `items` enqueues `ProbeFile` and `RefreshItemMetadata`, and both of those packages import `items` — so the constants cannot live with their jobs without a cycle. `jobs` imports nothing of ours, which makes it the one place every level can name the next, and the whole graph readable in one file.

`RefreshItem` then asks for the two things a new title needs, and only when it needs them: `ProbeFile` for a file whose `probed_at` is missing or older than it, and `RefreshItemMetadata` for a title carrying no `provider_ids`. So a title that lands in a refresh is probed and identified without waiting for either schedule.

The batch jobs stay, and are what makes the chain safe to lose: an enqueue that failed, a worker that died mid-run, a title TMDB gained since. `RefreshMetadata` selects every row whose `provider_ids` is null or that has no `image` row, so the next scheduled run picks up whatever the chain did not answer. An episode does not depend on its series being identified first — its key carries the series id — so nothing about the order matters.

Each enqueue is fire and forget, so a level never waits on the one below it and a failure stops one title rather than a library. The two jobs that used to ride along are their own now and run on their own schedule: `ProbeFiles` in `internal/probe` reads every file `items.SourcesNeedingProbe` returns, and `SweepItems` in `internal/items` is the reference count. Neither belongs to a refresh — one is bounded by ffmpeg and the other is a garbage collector.

**The sweep happens in the parent, before the fan out.** `RefreshLibrarySource` has fetched the complete list by the time it enqueues anything, so it holds the whole truth for that pair and does not need its children's results to know what went away — which is the thing fire and forget otherwise takes from you. It deletes files whose path the source no longer reports and membership whose key it no longer tags, then enqueues. Deriving the key from the TMDB id is what makes that possible: the parent knows every child's key without the child having run.

**A child resolves its parent by key, and the retry is what makes that safe.** `RefreshItem` for an episode looks up `season:tmdb:1396:1` and fails if it is not there yet. The parent is enqueued first, so this is only ever a race against the queue, and the activity retries it with backoff — a second, then two, four, eight, up to a minute apart, eight attempts, about three minutes of window. Three attempts on the default backoff was three seconds, which an episode queued behind ten thousand siblings loses every time.

Being generous costs nothing because every job is idempotent: `SaveScanned` and `SaveSource` upsert on a key and a path, membership is `DoNothing` on conflict, and a re-run writes what the first run would have. A retry that was not needed is one extra upsert.

**There is no `ScheduleToStartTimeout`.** It fails a job for having waited too long to be *picked up*, it is not retried, and it is measured against a queue this design deliberately fills — ten thousand probes at a couple of seconds each across `GOMAXPROCS` workers takes far longer than the ten minutes it used to allow, so it failed work that was merely backlogged. A queue nobody is serving is now bounded by the workflow execution timeout instead, and shows as running rather than as thousands of failures.

**One job per leaf, and that is thousands of executions.** A ten thousand episode Sonarr enqueues ten thousand `RefreshItem` executions. Each enqueue is a `StartWorkflowExecution` round trip, so `RefreshLibrarySource` issues them through an `errgroup` bounded at `enqueueConcurrency` rather than one after another; serially, ten thousand round trips was minutes of a listing doing nothing but waiting on the frontend. That is the shape Temporal is built for — independent top-level executions rather than one parent's history — but it is not free, and it is the reason the parent sweeps rather than waiting.

**A job names its own task queue.** `Job.Queue` is where `Service.Enqueue` and `Service.Start` put a run, empty meaning `jobs.TaskQueue`; the activity inherits the queue of the workflow that runs it. `RefreshMetadata` and `RefreshItemMetadata` are on `jobs.MetadataQueue` because they wait on a rate limited API while a probe saturates a core, and ten thousand identifies fanned out behind the same activity cap as the probes starve them. A new kind of per item work gets a queue of its own rather than a bigger cap on the shared one (#567). `RefreshLibraries`, `RefreshLibrary` and `RefreshLibrarySource` are on `jobs.RefreshQueue` for the mirror-image reason: they are the levels that fill `TaskQueue`, and on the shared queue a listing waited behind every `RefreshItem` and `ProbeFile` the previous one had enqueued. The worker's activity cap is `GOMAXPROCS`, which Go 1.25 reads off the cgroup cpu limit, so a worker capped at one cpu runs one activity per queue at a time and a source's listing could sit unstarted for as long as the probe backlog took. The worker runs one Temporal worker per queue `Registry.Queues` names, `TaskQueue` always among them, each with the same options and every job registered — so the queue decides only where a run waits, and a run started on a queue before its job moved still finds something to run it. An enqueue resolves the name through the registry, so a name nothing registered is refused at the enqueue rather than failing as an unknown activity.

**Scaling in does not kill a run.** On SIGTERM `Worker.Stop` stops every queue's poller at once and each waits up to `TEMPORAL_WORKER_STOP_TIMEOUT` for the activities it holds; whatever is still running after that has its context cancelled and is retried on another worker, which every job's idempotence makes safe. The default is zero, which cancels at once — the chart sets it from `worker.stopTimeoutSeconds` and derives `terminationGracePeriodSeconds` from the same number. fx bounds every `OnStop` hook to its own 15 second `StopTimeout` and exits non-zero past it, so `workerCommand` loads the config itself to raise that bound by the stop timeout; without it fx would cut the drain short whatever Temporal was told.

Triggers are not built. `UpdateTask` answers 501 rather than storing a schedule nobody reads; Temporal schedules are where they belong.

### Library sources

**A library is filled from Sonarr and Radarr rather than from a walk of its locations.** `internal/sources` owns the source rows and the clients under it, and `internal/items` writes what they answer into items and files. Nothing parses a filename any more: the title, the year and the season and episode numbers are what the instance already knows, so the regexes that guessed them out of `The.Matrix.1999.mkv` are gone along with the `filepath.WalkDir` that fed them. The scan reads no filesystem at all now: the probe is the only thing that opens a file, and it opens only files it has not seen before.

**The scan reads no artwork, no sidecar subtitles and no container tags.** Sidecar posters were a second artwork path for the case where an operator curated one by hand; `internal/metadata` fetches from the provider on a schedule of its own, so the scan is out of that business. Sidecar subtitles were the last directory listing in the scan — `Movie.en.forced.srt` parsed into an external `media_stream` — and they are gone with it, along with `media_stream`'s `path`, `is_external` and `is_hearing_impaired` columns and the whole `server/subtitle` tag package, which refused every embedded stream with a 501 and so had nothing left to serve. Subtitles are what ffprobe found inside the container. Container tags were worse than redundant: `genre`, `studio` and the `artist`/`composer`/`conductor` set are an audio-library feature read off ID3 and Vorbis tags, and a Sonarr- or Radarr-managed MKV carries none of them, so the code ran on every probe to find nothing. Genres and studios come from the provider now, off detail responses the identify job already fetches, which costs no extra call and answers for titles no container ever described.

Credits have no writer while that is true — `DistinctPeople` answers empty rather than wrongly, which is what `/Persons` served in practice anyway.

**The API key is not in the database.** A source stores the *name* of an environment variable — `SOURCE_API_KEY_RADARR`, say — and the key itself is only ever in the process environment. So a database dump, a backup and the config endpoint carry no credential, and rotating one is a redeploy rather than a write. `internal/env` collects every variable carrying the `SOURCE_API_KEY_` prefix into `Config.SourceAPIKeys` at load, which is what keeps `env` the only reader of the environment: a domain asks `sources.APIKey(variable)` rather than reaching for `os.Getenv`.

The prefix is a boundary, not decoration. Without it an administrator could name `DATABASE_URL` or `TMDB_API_KEY` as a source's key variable, point the source at a host they control, and have the server post the value to them; the scan refuses any name that does not carry the prefix, on the way in and again on the way out. A variable the config names and the environment does not hold fails that source's scan with what to set, rather than authenticating as nobody.

**A downloader owns its directories, and that is a claim rather than a hint.** Each `source_paths` row maps a `remote_path` the instance reports files under to the `local_path` this server opens them at, and a source has as many as it has root folders — one Radarr with `/movies` and `/movies-4k` is two rows, not two sources. A path outside every mapping is refused at scan time rather than passed through to `os.Open`. No two mappings anywhere may overlap on this server's side — `/media` and `/media/movies` are refused at save time, since `unique(local_path)` alone would admit them — and within one source no two may overlap on the instance's side either, because then a reported path would have two answers. `unique(path)` on `item_sources` is the same rule enforced by the database, so a second instance pointed at the same directory fails on its first colliding file rather than quietly producing duplicate versions. A mapping's `local_path` must also lie inside some library's folders, so what a downloader feeds is something an administrator already published as a library rather than any path typed into a box; `validate` refuses the rest. `Test` asks the instance for `/rootfolder`, and the dashboard offers only those on the instance's side and only library folders on this server's, with no free text on either — nor for the key variable, which is picked from `/GoJellyfin/SourceApiKeyVariables`.

**A source is bound to a library, not to a path**, and the binding is a row rather than a blob. `library_sources` carries the library, the source and the tag filter, unique on `(library_id, source_id)` and indexed on `source_id`, so "which sources feed this library" is a join and an index rather than a scan of every source decoding its own JSON. It replaced two `jsonb` columns on `source`, which could be neither joined nor constrained: nothing stopped a binding naming a library that had been deleted, and both sides cascade now.

Several instances may feed one library and one instance may feed several, which is what the tag filter separates: an empty filter takes everything the instance manages and a named one takes only what carries that tag. A tag the instance does not define fails the source rather than quietly taking nothing, because to the sweep an empty answer and a misspelt tag look the same.

**Deleting a library deletes the titles nothing else holds.** Items are global, so the cascade that used to take a library's items with it is gone; `DeleteLibrary` collects the ids first and removes those left in no library and not a playlist. Without that they survive with no membership, invisible to every library query and present in every global one.

**A library is a permission boundary.** `user_policy.enable_all_folders` and `enabled_folders` decide what a user sees: an item is visible if it holds membership in a library they can access, and a playlist is exempt because it belongs to its owner rather than to a library. `users.Access` answers what one may see and `dto.ViewerFor` turns that into an `items.Viewer`.

**The viewer is a parameter, never read off the context.** Fifty files import `internal/items`, and that is the point — a signature makes the compiler name every read that needs one, and a background job passes `items.Everyone` where a reader can see it. The zero value sees *nothing*, so a caller who forgets it gets an empty result rather than someone else's library; that is what made the two query structs announce their missing callers when the tests went red. It rides inside `ItemQuery`, `MetadataQuery` and `EpisodeQuery` for the listing paths, which is where browsing and search discover anything.

**An anonymous request resolves to no access, and that decision lives in `users.Access`.** The authorization middleware already refuses anonymous access to every operation outside `PublicOperations`, so a handler reached without a user is public by declaration — the image endpoint is the only one, and it passes `Everyone` explicitly. Keeping the rule in the policy service rather than in the caller is what lets a test inject a permissive stub deliberately instead of every fixture having to build a session.

**A library nobody bound is left alone.** `scanLibrary` returns before the sweep when no source names it, so creating a library and scanning it before binding a source does not empty it.

**A source is edited by its id, one at a time.** `/GoJellyfin/Sources` creates one and `/GoJellyfin/Sources/{sourceId}` reads, replaces and deletes one. A save used to replace the whole list and match on the URL, so changing an instance's address, or a save that left one out, deleted the source — and since a file belongs to its source, that took every `item_source`, `media_stream` and membership row with it and re-probed the library. Now a source goes away only when it is deleted by id, and `Update` keeps the bindings it still names in place, for the reason given below. A refused save is a `400` carrying the reason, because the dashboard has to say which folder collided. URL and name stay unique, so two rows cannot describe one instance.

**A source records whether its instance answers.** `RefreshLibrarySource` asks `/system/status` before it lists anything and writes `version`, `contacted_at` and `last_error` on the source, so the dashboard card says when the instance last answered without anyone reading the job history. That is the instance's health, not the binding's: what a binding last synced is `library_source.last_synced_at`, below. `/GoJellyfin/SourceApiKeyVariables` lists the `SOURCE_API_KEY_*` names the server holds — names only, never values — so the key is picked from what is set rather than typed and found misspelt at scan time. It is not under `/GoJellyfin/Sources/` because the mux matches in registration order and `{sourceId}` would claim it.

**Sources are read in name order**, which is the only thing deciding whose artwork wins when two instances report one title. Which of an item's files is *played* is not decided here at all — that is `items.SourceFor`, on the probed streams (see Transcoding).

**`internal/sources/arr` is the vocabulary Sonarr and Radarr share** — the tag list, the file record and the `X-Api-Key` header, which are the same on both — and `radarr` and `sonarr` hold only what differs. The domain makes the requests and translates both into a flat `[]sources.Title`, each carrying its own key and its parent's, so the fan out is a loop rather than a recursion and no consumer learns which instance answered. An episode Sonarr has no file for is not a row: only what is on disk becomes an item, so the library holds what can be played rather than what has been wanted.

**A file remembers what the instance calls it.** `item_source.external_id` is the instance's own id for the title behind the file (a Radarr movie, a Sonarr episode) and `external_file_id` its id for the file record, indexed with `source_id`. They live on the file rather than the item because the item is global and one title can come from several instances, each numbering it differently. Nothing reads them yet: they are what an *arr webhook names, so they are the lookup incremental sync needs, and a full read is the only sync until that lands.

**A binding says when it last read.** `library_source.last_synced_at` is stamped by a `RefreshLibrarySource` that succeeded and `last_error` is what the last one that failed said, cleared by the next success, so a failure keeps the time of the last good read beside the reason it stopped. Both ride out on `GET /GoJellyfin/Sources` as `LastSyncedAt` and `LastError`. Saving sources upserts each binding on `(library_id, source_id)` rather than deleting and recreating them, because a recreated row is one that has never synced.

**The kind enum is what something writes.** `Movie`, `Series`, `Season` and `Episode` come from the scan, `Playlist` from `internal/playlists`, and `Audio` is kept for the audio route and for Lidarr. The rest of Jellyfin's `BaseItemKind` (`BoxSet`, `Folder`, `Trailer`, `CollectionFolder` and the others) had no writer and read as features that exist; `CollectionFolder` and `Folder` are built in `dto` from libraries rather than stored. The database holds both rules as checks: `item_kind_known` on the enum and `item_key_unless_playlist`, because a playlist is the one item no source names. `itemKinds` in the schema is the one list both are built from. A client asking for a kind not in it is answered nothing rather than everything, which is why a query's `Kinds` is a filter when it is non-nil, even empty, and absent only when nil.

**Paths arrive in the instance's namespace**, so the source's mappings rewrite them into what this server can open; a source whose two paths are equal is one that shares a filesystem with the server.

**A title's runtime comes from the provider; a file's comes from the probe.** They are different facts, and the probe used to write whichever file it read last onto the title — the same defect that took `container` and `probed_at` off `item`, except this one is read. `items.Metadata` carries it now, the file keeps its own on `item_source`, and the DTO falls back to the file's until an identify run has answered. `has_subtitles` went the same way: it is derived from the file's streams rather than stored on the title.

**`dateAdded` is what the scan stores as the file's `date_modified`, and it is not the file's mtime.** Sonarr and Radarr write a new file record each time they import one, so an upgraded release moves the date and earns a re-probe, while a file replaced underneath them in place does not and keeps the probe it has.

**TMDB is the one canonical provider, and the key is namespaced by it.** No provider covers all four kinds — Radarr requires `tmdbId` so a movie always has one, Sonarr is TVDB-primary and maps to TMDB through its metadata server, and neither answers an id for a season, nor a usable one for an episode. So the id identifies a movie and a series, and a season and an episode derive theirs from the series above them. TMDB rather than IMDb because `imdbId` is frequently empty on both sides and there is no IMDb id for a season at all, and rather than TVDB because TVDB has nothing for a movie.

A series Sonarr reports with `tmdbId` 0 is **skipped and logged**, not keyed on a fallback. Falling back to `tvdb:` looks harmless until Sonarr learns the mapping: the key becomes `tmdb:` on the next run, the upsert creates a second row, and the watch state stays on the orphan — the exact failure the key exists to prevent. A skipped series is visible in the log and fixed by a refresh in Sonarr.

The name and year no longer decide identity, which is what makes two films sharing both stop colliding, and what stops a retitle in Radarr moving a title's key.

### Metadata providers

**`internal/metadata` is what anything else names; `internal/metadata/tmdb` is one implementation of it.** It sits under `metadata` because nothing outside `metadata` calls it, and the tree should say so. The interface is declared by the consumer, in `metadata/provider.go`, and `metadata.Module` aggregates `tmdb.Module` the way `server.Module` aggregates its tag packages — so `server.go` and `worker.go` list `metadata.Module` and learn nothing about who answers. The scheduled task the dashboard shows says it identifies items, not who it asks.

That split is a rule, not a preference: **no package outside `internal/metadata` may import the provider.** `TestProviderStaysBehindMetadata` in `internal/metadata/boundary_test.go` fails naming any file elsewhere that imports it.

The rule is about imports, not about the letters T-M-D-B. `internal/env` carries a `TMDB` struct holding `TMDB_API_KEY`, and that is correct rather than a leak: `env` is the one place every variable this binary reads is written down, and the variable is named for the service whose key it is because that is what an operator puts in a manifest. A provider-neutral name would make the manifest lie and would break the moment a second provider needs a key of its own. `env` imports none of our packages, so naming a variable costs no coupling — the leak to avoid is a package reaching for the provider, and `metadata` still takes only the `Provider` interface.

`metadata` owns the job, the batch loop and the locks. `tmdb` owns the calls and the translation from TMDB's payloads into `items.Metadata` — including from TMDB's vocabulary into ours, which is why `Status` is mapped to Jellyfin's `Continuing`/`Ended`/`Unreleased` rather than passed through, and why a movie writes no series status at all.

The calls go through `github.com/cyruzin/golang-tmdb`, which models every payload this needs. Two of its behaviours are deliberately not used. Its `SetClientAutoRetry` retries a 429 in an unbounded loop and never retries a 5xx, so a `RoundTripper` in `retry.go` does the backoff with a bound; and every request it builds carries its own `context.Background`, so a cancelled run cannot interrupt one in flight — the limiter before each call is where cancellation lands, which bounds a cancelled step to a single request's timeout.

A miss is a `false` return rather than a sentinel error, so the implementation never imports its consumer for one variable. The interface takes a TMDB id rather than something provider neutral, because the id is what the key is built from (see Library sources) — a second provider would need a key that carries its id first.

There is **one** provider and one binding — no fx value group and no priority order until a second provider exists to need them. The seam is the interface.

It is bring your own key: `TMDB_API_KEY` reaches the client as `env.Config.TMDB.APIKey` rather than through `os.Getenv`, and unset leaves the provider disabled and the job a no-op, so a developer running the server alone still gets a server. An absent key is deliberately not a validation failure — `env` refuses a malformed value, not a missing optional one. We embed no key of our own: there is then none to share, none to throttle and no attribution owed for one.

The job runs on its own rather than inside the scan, and fans out: `RefreshMetadata` selects what needs identifying and enqueues one `RefreshItemMetadata` per item, in no particular order, so each item is its own execution with its own retries and one bad title fails alone. The provider's limiter is what bounds the request rate, not the batch. What a run still leaves, the next run picks up.

The batch is derived from the rows — `items.ItemsNeedingMetadata` asks for items whose `provider_ids` is null or that hold no `image` row — rather than handed over, so a crash re-asks the question instead of replaying a stale list.

**An identified item with no artwork is not finished.** `provider_ids` alone used to decide, so a title identified while `/configuration` was unreachable, or before artwork had a table, or whose rows `drop_image_bytes` deleted, kept its metadata and stayed a placeholder forever: nothing asked again short of a forced refresh. The batch takes those back, so the next scheduled run is the backfill and no migration has to call the provider. The price is that a title TMDB has no picture for is asked again each run, the same price an unmatched title already pays, and it stops the run TMDB gains one.

**Every lookup is by id, and the id comes out of the item's own key.** `items.TmdbID` reads it back out of `movie:tmdb:603`, so identifying a title is one request to `/movie/603` rather than a search for its name followed by a fetch of whatever came back first. That halves the requests and removes the guess: a search returned `Results[0]`, so two films sharing a title and year were a coin toss, and a title Radarr had renamed searched for the wrong thing.

A season and an episode carry the *series'* id in their own keys — `season:tmdb:1396:1` is series 1396 — which is exactly what `/tv/1396/season/1` wants. So a season never looks at its series row and **does not need the series identified first**, which is why the batch has no order and an identified series sends nothing back for its children. Specials are season zero on both sides and need no case of their own.

An item whose key carries no TMDB id is a miss rather than an error and asks the provider nothing; nothing writes such a key, so only a row left by an older scan has one.

**Artwork rides on the metadata rather than costing a call of its own.** TMDB puts `poster_path`, `backdrop_path` and `still_path` on the detail responses the identify job already fetches, so `items.Metadata` carries the references and the run makes no extra request against the rate limited API. `tmdb` returns references and never bytes — it is a translation layer — and `metadata` writes each one as an `image` row holding the url (see Images). The one new call is `/configuration`, read once per process and cached **on success only**, so a process that started while TMDB was unreachable is not left without artwork until somebody restarts it; a configuration that cannot be read costs that item its artwork, not the run its metadata.

Sizes are fixed — `w780` posters, `w1280` backdrops, `w300` episode stills. Clients send `maxWidth` and `fillWidth` and nothing here reads them, so a second size would be stored and never asked for; server-side resizing is what would make those parameters mean anything.

A write that fails is logged and stepped past, per image — the loop heartbeats and checks `ctx.Err()` between them, the same as the item loop above it.


`lock_data` and `locked_fields` are Jellyfin's semantics and `metadata` honours both. `LockData` keeps an item out of the batch entirely; a field named in `LockedFields` is dropped from what is written, by `stripLockedFields`, which takes a pointer because it edits what it is handed and hiding that would hide an overwrite later. The provider ids themselves survive a field lock, because they are identity rather than metadata and Jellyfin has no lock for them.

One request per item, not more: the detail call carries `append_to_response=release_dates` (or `content_ratings,external_ids`), so the certification, the IMDb id and the credits arrive with the record instead of costing another round trip. A 429 or a 5xx backs off and retries rather than failing the run; a 404 is a miss, which is not an error because the title may be one TMDB gains later.

The two packages test at their own seam: `metadata` runs the loop and the locks against a stub provider and a real database, and `tmdb` points its client at an `httptest.Server`. A green run needs no key and CI never calls TMDB.

### Images

**An image row is a url the provider answered, and no row holds bytes.** `image` carries the item, the kind, the index, the `url` and a `tag`, and `GET /Items/{id}/Images/{type}` answers `302` with that url in `Location`. So there is no blob table, no storage backend, no download, no size limit and no sweep of orphaned bytes — a poster is fetched by the client from TMDB's CDN, which is where it was going to come from anyway. What was here before was `internal/artwork` over `image_blobs`, plus a fetcher in `internal/metadata` that knew about storage keys, plus `items.SaveDownloadedImage`: three packages for one row.

**The tag is the sha1 of the url**, which is what makes `?tag=` bust a client's cache when TMDB changes a poster: a different picture is a different url, so a different tag, and `SaveImage` upserts on `(item, kind, index)` so the row is rewritten in place.

**A landscape card falls back through the parents, and the DTO has to name them.** `jellyfin-web`'s Continue Watching and Next Up rows ask for `Thumb`, then `ParentThumbItemId`, then the item's own `BackdropImageTags`, then for an episode `ParentBackdropItemId`/`ParentBackdropImageTags`, and only then `Primary`. TMDB has no thumb, so a movie's card is its backdrop and an episode's is its series' backdrop; `dto.applyShowFields` writes the series' `Backdrop` and `Thumb` onto its seasons and episodes as the `Parent*` fields, the same lookup that already fills `SeriesPrimaryImageTag`. A movie with neither a backdrop nor a poster is the clapperboard.

**`internal/metadata` is the only writer.** It is handed `items.RemoteImage` references by the provider on the same detail response it already fetched, and writes one `image` row each. The scan writes none — there is no local artwork path any more (see Library sources).

**A library card is a collage, built when it is asked for and held in memory.** `internal/collage` takes the ten newest top-level posters `items.LibraryPosters` answers, fetches their urls off the CDN, crops each into a five by two grid at 960x540 to match the `overflowBackdrop` card, and answers a JPEG on `GET /Items/{libraryId}/Images/Primary`. Nothing is stored: the bytes live in a map keyed by library and are the one place this server holds image bytes at all, which is why the blob table did not come back with them. The tag is the sha1 of the poster tags that went in, so `dto.LibraryView` advertises one only when a library has posters — `jellyfin-web`'s `getCardImageUrl` leaves the url null without a tag and draws the collection type's icon instead of a broken image — and a library gaining a poster is a new tag, a new url and a rebuild, with no clock and no expiry. That is also why the response carries the same day-long `Cache-Control` as a redirect.

A collage is held only when every poster made it in. One that a CDN failure left short is served with `no-store` and rebuilt on the next ask, because its tag is the same one a complete collage would carry and a client told to keep it for a day would never ask again, so an outage at the first request does not freeze a gap into the card until a poster changes. Builds of one library and one tag collapse through `singleflight` and run detached from the asking request, so a client that goes away does not fail the build for the others waiting on it; the fetch timeout is what bounds it. The image endpoint is public, so a request for an id with no posters costs one indexed query and stores nothing.

**A shelf card is the same collage, built from what the shelf lists.** `collage.Service` asks `shelves.Posters` before `items.LibraryPosters`, so `GET /Items/{shelfId}/Images/Primary` answers the first ten posters of the shelf's own `/Items/Latest` and `dto.ShelfView` advertises its tag the way `LibraryView` does. `items.Posters` puts an episode's series poster in its place, because a still is landscape and the grid's cells are poster-shaped. Only a shelf that reads the same for everyone has one — `fixed` and `seasonal` set `shared` — because the image endpoint is public and knows no user: `hidden-gems`, `short-on-time`, `because-you-watched` and `genre-spotlight` keep the collection type's icon, and so do the trending shelves, whose posters live in `discover` rather than in `image` rows. The shelf is read as `items.Everyone`, as a library's collage already is. A newly aired episode is a new poster list, so a new tag and a rebuild, with nothing to expire.

### Home rows

**The home screen's rows are the client's, so a new row is a library the client is told about.** `jellyfin-web` 10.10 draws a fixed set of sections chosen by `homesection0`–`9` in the display preferences, and there is no section type of our own. The one that expands is `latestmedia`: it draws a row for every view `/UserViews` answers, skipping ids in the user's `LatestItemsExcludes` and the `playlists`, `livetv`, `boxsets`, `channels` and `folders` collection types, and fills each from `/Items/Latest?ParentId=<view>`. The title is the client's translation `Recently Added in {name}`, so a shelf named `Recently Aired` would read `Recently Added in Recently Aired`. No response field changes that prefix, so the branding stylesheet does: the heading sits inside a link whose `href` carries the view's id, and `branding.brandingCss` appends a rule per shelf that pushes the heading's own text out with `text-indent` and draws the shelf's name in `::after`, which keeps the heading's font and colour because nothing about them is restated. The rules are keyed on shelf ids, so a real library's row is untouched, and they are appended on the way out like the SSO button, so the stored custom CSS the dashboard edits never holds them. `/Branding/Css` is fetched before sign-in and is the same for everyone, so only a shelf whose name is fixed gets one (`shelves.Titles`); `genre-spotlight` and `because-you-watched` are named per week and per user and keep the prefix. It reaches `jellyfin-web` and the apps that wrap it. A native client (Android TV, Swiftfin, Roku) loads no custom CSS and writes its own row titles.

**`/Items/Latest` groups the way upstream does.** `items.LatestItems` reads five times the limit of movies and episodes, newest first, and folds episodes into their series: a series holding one is answered as that episode with `ChildCount: 0`, which is what makes the client's `getCardImageUrl` draw the series poster for it, and a series holding several is answered as the series. Added means `item.date_modified`, which is the newest `dateAdded` Sonarr or Radarr reported for its files, and `created_at` only where that is missing, so importing an old library does not put every title at the front. The badge on a series card is `UserData.UnplayedItemCount`, not `ChildCount`, and nothing writes that yet.

**A shelf is defined in `internal/shelves/catalogue.go`, and only whether it is on is stored.** Each is a slug, a collection type and an `items.LatestQuery`. Which are on is one `configuration` row keyed `shelves`, a JSON list of slugs that the admin app's Settings screen writes through `PUT /GoJellyfin/Shelves`; no row means `shelves.Defaults` (`recently-aired`, `new-releases`), and a slug nothing defines is refused at the save. It was the `SHELVES` variable, and moved because a value lives in the environment or in the database, never both, and a shelf is an editorial choice rather than deploy policy. The row is read per request, so every replica agrees the moment it is saved. A shelf's id is a uuid derived from the slug, so it is stable across restarts and replicas with nothing stored. `userviews` appends them to the libraries, and the `items` tag asks `shelves.Shelf` before it treats a `ParentId` as a library. A shelf whose query has nothing to say this request — `spooky-season` outside October, `because-you-watched` for someone who has finished nothing — is left out of `/UserViews` rather than drawn empty. Every one is also a My Media tile, which is why most are off by default.

### Titles the library lacks

**A title the library does not hold is an item with no row.** `internal/discover` lists what the provider calls trending, drops whatever `items.HeldKeys` says the library already has, and hands the rest out as `discover.Title`s that `dto.UnownedDto` draws as an ordinary `Movie` or `Series`. Two shelves carry them, `trending-movies` and `trending-shows`, both off until Settings turns them on and both left out of `/UserViews` while there is no `TMDB_API_KEY`; a shelf with `Unowned` set is answered by `discover.Trending` rather than by an `items.LatestQuery`. This is the surface requests are made from, and nothing here makes one yet.

**The id is the kind and the TMDB id, written into a uuid.** `discover.ID` puts a fixed eleven-byte prefix, one byte of kind and the TMDB id in the last four, and `discover.Parse` reads them back, so `GET /Items/{id}` and `GET /Items/{id}/Images/{type}` are answered for a title no replica has ever stored and no table had to be written for a row somebody merely scrolled past. It is not a hash, because a hash cannot be read back, and it is not a row, because trending is twenty new titles a week that nobody asked for. A movie and a series sharing a TMDB id differ in the kind byte. Once the library holds the key a title's id names, `GetItem` answers the real item for it, so a client still holding the old id lands on the thing it can play.

**What makes it unplayable is what the DTO says, not a missing file.** `LocationType: Virtual` is what `jellyfin-web`'s `playbackManager.canPlay` refuses for anything but a `Program`, so a movie's detail page draws no Play button, and `PlayAccess: None` says the same to a client that reads that instead. A `Series` is the exception: `canPlay` answers true for the type before it looks at the location, so a show the library lacks still draws Play, and pressing it finds no episode. The favourite button is drawn either way, which is the reason for the whole shape.

**The trending list is asked for once an hour per kind and the detail record once a day per title, in memory.** A row's twenty cards ask for twenty posters, so the summaries the list carried are kept and `discover.Summary` answers an image from one without a request; `discover.Title` is the detail page's and fetches the whole record, which is never replaced by a later summary. A provider that stops answering serves the last list rather than an empty row. The cache is per process and bounded by dropping all of it at `detailLimit`, because every entry can be fetched again.

`TMDB_BASE_URL` exists for `make e2e`, whose `setup/tmdb.js` answers the configuration, the two trending lists and a detail record apiece; unset means TMDB itself. The stub names its artwork under the proxy's `/fixture-posters`, since the specs let the browser through to that origin only.

### Requests

**The heart on a title the library lacks is the request.** No client has a request button and every client has a favourite, so `userlibrary.saveFavorite` asks `discover.Title` whether the id is an unowned one before it treats it as an item: a held key is favourited as the real item it has become, and anything else goes to `requests.Request`, which adds the title to Radarr or Sonarr. Taking the heart off is `requests.Withdraw`, which forgets that this user asked and tells the instance nothing — the download is the instance's from the moment it accepts, and removing a film from Radarr because one of three people changed their mind is not ours to do.

**Who asked and what an instance was told are two tables.** `request` is unique on `(user_id, key)` and is why a title reads as requested; `request_submission` is unique on `(source_id, key)` and carries `accepted_at` and `last_error`, so a second user hearting the same film adds a row to the first and posts nothing, and an instance that refused is asked again by the next heart rather than remembered as done. The key is the item key the scan will write (`movie:tmdb:603`), so the moment the file lands `items.HeldKeys` drops the title from the trending row and the request has nothing left to point at but history.

**A source takes requests only when it names a quality profile.** `source.request_profile_id` nil is off, which is the default, and `request_root_folder` and `request_tag` ride beside it: the folder must lie within one of the source's own remote paths, because a film downloaded somewhere no mapping covers is one the scan then refuses, and the tag is how a request lands in the library a `tag_filter` feeds. A request goes to every source of its kind that takes them, in name order, so a 4K Radarr and an HD one both configured both get it. With none, `requests.ErrNowhere` reaches the client as a 403 and the heart does not stick. The dashboard picks all three from what `Test` answers — `/qualityprofile`, `/rootfolder` and `/tag` — with no free text.

**The add is the instance's own lookup record sent back.** Radarr answers `movie/lookup/tmdb?tmdbId=` and Sonarr `series/lookup?term=tvdb:<id>` with the record their `POST` wants, title slug and images and all, so `sources.Submit` adds the profile, the folder, `monitored`, the tags and the search option to what it was handed rather than building a payload field by field. A record that comes back with an `id` is one the instance already manages, which is success without a post. Sonarr adds by TVDB id and TMDB is what a title here is keyed on, so the series detail call's `external_ids` puts `Tvdb` in `ProviderIds` and a show TMDB has no TVDB id for is refused with that as the reason.

**A search finds what the library lacks too, but only what a heart could then ask for.** `GetItems` with a `SearchTerm` and no parent, favourite filter, ids or offset is what `jellyfin-web`'s search page sends once per type, and `items.searched` appends up to ten of the provider's matches for `Movie` and `Series` after the library's own. A kind is searched only when `requests.Taken` says some source takes requests for it, so a server with a TMDB key and no downloader to ask does not fill its search with titles nobody can get; the trending shelves are not gated that way, because an administrator turned them on. The provider failing costs the search its unowned titles and nothing else. What comes back is remembered the way a trending summary is, so the cards' posters cost no further request. `jellyfin-web`'s search page asks `/Artists` beside its `/Items` queries and draws `No results found` for the whole page when any one of them fails, so `server/artists` answers an empty list rather than the 501 it used to: there is no music to find, and the 501 hid every film the other queries had found.

**What a user may ask for is three columns on `user`, and the default is everything.** `can_request` false refuses the heart, `request_quota` is the most titles in `requests.QuotaWindow` — seven days, counted off `request.created_at`, nil meaning no limit — and `requests_need_approval` records the request as `Pending` and asks no downloader until an administrator approves it. An administrator's own requests never wait. All three refusals reach the client as the 403 `ErrNowhere` already was, because a heart has no way to say why. Asking again for a title the user already asked for costs no quota and re-submits an approved one, which is how a refused add is retried from a client.

**The queue is `/GoJellyfin/Requests`, and Approve is also the retry.** `requests.Queue` groups the request rows by key, newest first, with each downloader's answer beside them; `Approve` marks one request approved and submits to every source that has not accepted the title, so pressing it on an approved request whose Radarr refused asks Radarr again. `Decline` marks the row and tells nobody: a declined request marks nothing on the title and still counts against the week's quota, since the user did ask. `request.tvdb_id` is stored for that later submit, because an approval happens with no detail record in hand. The dashboard's Requests page is the second entry in `dashboard.pages`, which is a slice rather than a map so the nav keeps its order, and `GetDashboardConfigurationPage` picks the body by `name`.

**"Requested" is the title's first tagline.** `jellyfin-web` draws `Taglines[0]` under the name and nothing else an unowned DTO carries is free to spend, so `dto.UnownedDto` prepends it when anyone's request is approved, or "Awaiting approval" while every one is pending, and `UserData.IsFavorite` is true only for the user who did. `e2e/setup/radarr.js` is the instance `requests.spec.js` hearts a film against; `/added` on it is the test's window, not Radarr's.

### Reports

**A report says a copy is broken, and the only thing it can do about it is ask the downloader for another.** `report` carries the item, optionally the file and the user, a `kind` (`Unplayable`, `Video`, `Audio`, `Subtitles`, `Other`), an `origin` (`User`, `Delete`, `Probe`, `Playback`) and a `status` (`Open`, `Resolved`, `Dismissed`). `internal/reports` owns it, and `reports.Takes` is the one answer to what can be reported: a movie or an episode, because those are what a file hangs off.

**Delete in a client files a report and deletes nothing.** Every client has a Delete button and none has a report button, the same reasoning that made the heart a request. `dto.ItemDto` answers `CanDelete` true for what `reports.Takes`, which is what makes `jellyfin-web` and the native apps draw the button for every user, and `library.DeleteItem` files `Unplayable` with origin `Delete` and answers 204 without consulting `EnableContentDeletion`. The client's own confirmation still says the file will be deleted, and nothing the server sends changes that text. A series, a season and a playlist still take the old path, and `DeleteItems`, the bulk spelling, is unchanged.

**`GET /report` is the page that can say what is wrong.** It is registered beside `/link` because it is a page rather than an operation, served `no-store`, and it reads the token `jellyfin-web` keeps in `localStorage` under `jellyfin_credentials`, so it only works on the origin the client is served from. It lists what the user was last watching, searches, walks a series down to an episode, and posts `/GoJellyfin/Reports`. `?item=<id>` opens it on a title. Nothing in a stock client links to it; a `menuLinks` entry in `jellyfin-web`'s `config.json` is what would (#687).

**The server reports what it finds itself.** `probe.ProbeSource` files origin `Probe` when ffprobe exits non-zero on a file that is there; a file that is not there is the sweep's to find, and a timeout is storage rather than the file. `stream.Handler` files origin `Playback` when a file it was asked for cannot be opened, when ffmpeg exits before its first byte, and when it exits partway through, and not for `ErrBusy`, `ErrNotAvailable` or a client that went away. A death partway through is told apart from a client leaving by which side failed: `process.Read` answers ffmpeg's exit as `transcode.ErrExited`, a failed write to the client is any other error, and the relay reports only `ErrExited` while its own context is still live. The context is what rules out the two kills — the stall timer cancels it before it kills, and a client that goes away cancels the request's — since either makes ffmpeg exit non-zero too.

**One open report per thing said.** `File` answers success without writing when an open report already says the same kind from the same origin about the same file by the same user. A report nobody filed by hand is also held back by a dismissed one, because the probe runs on a schedule and a file an administrator has already waved through would otherwise come back every run; a resolved one does not hold it back, since a replacement that is broken too is news.

**Replace is delete, blocklist, search, in the downloader's own words.** `sources.Replace` looks up the newest `grabbed` history record for the title, deletes the file record, marks that grab failed (which is what puts the release on the blocklist) and starts a search. Radarr spells those `history/movie?movieId=`, `moviefile/{id}`, `history/failed/{id}` and the `MoviesSearch` command; Sonarr `history?episodeId=&eventType=1`, `episodefile/{id}`, the same `history/failed/{id}` and `EpisodeSearch`. A file nobody grabbed, one imported by hand, is deleted and searched for with nothing to blocklist. It needs `item_source.external_id` and `external_file_id`, which the scan writes, so `reports.Replaceable` is false for a file from before those columns until the next refresh. `reports.Replace` resolves every open report on the title once the downloader has answered, and leaves them open when it refuses.

**The queue is the Requests and Reports dashboard page.** `/GoJellyfin/Reports` lists and files, and `/GoJellyfin/Reports/{reportId}/Resolve`, `/Dismiss` and `/Replace` decide; filing needs a signed-in user who can see the title and the rest need an administrator.

### Admin app

**`/admin` is a second admin UI beside `jellyfin-web`'s dashboard, and it is ours.** `admin/` is a Vite, TypeScript and Preact app whose API types are generated from `spec/jellyfin-openapi-stable.patched.json` by `openapi-typescript` at build time, so renaming an operation or a field fails `tsc` rather than a browser. `internal/server/admin` embeds `internal/server/admin/dist` and answers `GET /admin` and everything beneath it, registered beside `/link` and `/report` because it is pages rather than operations: a file that exists is served, `assets/` with a year-long immutable `Cache-Control` because Vite names them by hash, a missing asset is a 404, and every other path is `index.html`, `no-store`, with `{ServerId, SingleSignOn}` written into its `gojellyfin-admin` meta through `html/template`. `dist` is gitignored except a `.gitkeep`, which is what lets `//go:embed all:dist` compile in a checkout that never built the app; such a binary answers `/admin` with a 503 naming `make admin`.

`make admin` is a file target on `dist/index.html` over everything under `admin/` and the patched spec, so `make build` pays for npm only when one changed. The `Dockerfile` builds it in a `node:22-alpine` stage, CI's `admin` job typechecks and builds it, and `e2e/setup/boot.js` builds it before the binary. `admin.spec.js` drives it under the same harness as the rest.

It signs in with the token `jellyfin-web` leaves in `localStorage` under `jellyfin_credentials`, the same one `/report` reads, and falls back to `AuthenticateByName` or single sign-on. `/sso/oidc/start?redirect=/admin` lands back on `/admin` rather than `/web/#/admin`, because the callback sends a return of `/admin` or beneath it to the path and every other one to `jellyfin-web`'s hash. A signed-in user who is not an administrator is told so rather than shown screens the API would refuse.

Each screen talks to the API a client already uses (`/Users`, `/Devices`, `/Sessions`, `/ScheduledTasks`, `/System/ActivityLog/Entries`) or to the `/GoJellyfin/` extension in `spec/gojellyfin.json`. `?mock` renders every screen from `admin/src/mock.ts` with no server behind it, which is the agreed design for the screens not wired yet; outside it the nav lists only the screens in `wired` in `app.tsx`.

**`GET /GoJellyfin/Settings` is every variable `env.Config` reads, and a secret is only whether it is set.** `env.Config.Variables` walks the struct the way `keys` does, so a new variable shows up with no second list to keep. A field tagged `secret:"true"` (`DATABASE_URL`, `TMDB_API_KEY`, `OIDC_CLIENT_SECRET`) and every `SOURCE_API_KEY_*` answers `Set` and never a value; `TestConfig_Variables` holds that. A value lives in the environment or in the database and never both: the environment is deploy policy and every credential, the database is what an administrator edits, and the Settings screen shows the first read-only beside the second.

### SyncPlay

A group is rows — `SyncPlayGroup` and `SyncPlayGroupMember` in `internal/store/entities`, behind `internal/syncplay`. It is not a map in the process, because several replicas sit behind a gateway that splits on path rather than session: `POST /SyncPlay/New` on one pod and `GET /SyncPlay/List` on the next are ordinary consecutive requests from one client, and an in-process group would answer the second with nothing. That is a group picker that works about one time in N rather than a degraded mode worth shipping.

**Membership is keyed on the session, not the user.** `sync_play_group_members.session_id` is unique, so one user on a phone and a TV is two participants, which is what upstream does. The row cascades from `sessions`, so signing out cannot leave a group holding a participant who is gone.

**Emptiness is a query, not a delete.** `List`, `GroupByID` and everything reached through them require `HasMembers`, so a group nobody is in is unreachable however it emptied — the last member leaving, or the cascade firing when their session was deleted. Disbanding it with a `DELETE` instead was tried and is worse: it only covers the leave path, and it races a concurrent join, where the join's foreign key insert and the delete's own row lock decide the order between them. Nothing deletes a group row today, which is what makes `join` a plain upsert on the session's unique index and therefore idempotent under a double-click. The rows a group leaves behind are collected in #616.

**Updates reach members on any pod**, through `internal/notify` over Postgres `LISTEN`/`NOTIFY`. A pod publishes an envelope naming the sessions it is for; every pod receives every envelope and drops what it does not hold, so no pod asks the database who is in a group. The publishing pod receives its own envelope the same way rather than short-circuiting local delivery, so there is one path rather than two. `internal/server/socket` holds the per-session registry and skips a session it does not have; its `enqueue` never blocks, so neither a member on another pod nor a wedged one can stall delivery to the rest.

### Request identity

`internal/auth` owns identity on the context — it puts it on and takes it off, and nothing else knows the keys exist. `middleware.Auth` only parses what the client sent (`Authorization: MediaBrowser …`, `X-Emby-Token`, `?api_key=`) and calls `auth.Authenticate`, which resolves the token through `sessions` and returns a context carrying the session.

`auth.UserID` reads the session's user edge, so `sessions.ByToken` has to eager-load it; the foreign key is unexported and there is nothing to fall back on. Nothing else hangs off that query — an edge is eager-loaded when a caller reads it, not in anticipation of one, because `ByToken` runs on every authenticated request and each edge costs another round trip.

**A disabled account's token resolves to nothing.** `IsDisabled` is refused in two places and no handler names it. `users.Satisfies` refuses every scope, which covers the generated operations, and `sessions.ByToken` carries the policy as a predicate beside `RevokedAtIsNil`, which covers the rest — `GET /socket` and the media urls call `ByToken` directly and never reach the authorization middleware, so a check that lived only there would leave a disabled account streaming. It is a predicate rather than an eager load, so it costs a subquery on a query that already runs per request rather than another round trip; the shape is `Not(HasPolicyWith(IsDisabled(true)))` so a user with no policy row still authenticates. Live tokens stop the moment the box is ticked and work again if it is unticked, which is what a soft flag should do. `AuthenticateUserByName` checks the same flag off the policy edge `UserByUsername` already loads, because a refused token is no help if a disabled account can mint a fresh one. `UpdateUserPolicy` refuses to disable an administrator, as upstream does, because nothing re-enables an account short of the database and an administrator who ticks their own box would otherwise lock the server. For the same reason `users.SavePolicy` and `users.DeleteUser` refuse a write that leaves no administrator, answering `ErrLastAdministrator` as a 403 the way upstream does: both lock the administrators' policy rows, write, and roll back if the count went from some to none, so two administrators demoting each other at once cannot both win. The SSO sign-in's `OIDC_ADMIN_GROUP` sync is exempt, because the provider is the authority for its own group. The rule is global, which a shared test database cannot hold still, so `internal/users` tests it in a scratch database of its own made with `Schema.Create`, and fixtures elsewhere delete their users through the client rather than the service. `AccessSchedules` is still stored and unread — it needs a timezone, a controllable clock and a decision about a stream that is playing when the window closes, which is #633.

**Changing a password revokes every session the account had.** `sessions.RevokeForUser` writes `revoked_at`, which `ByToken` and `List` already filter on, and both password paths call it — `UpdateUserPassword` and `gojellyfin resetpassword`. There is no carve-out for the caller's own session: the reason to change a password is usually that a token is loose, and a change that leaves the loose one working is not one. The client is logged out and logs back in.

**The client's address is the peer's unless the peer is a proxy this server trusts.** `TRUSTED_PROXIES` is a list of networks, and `middleware.HttpClientAddress` rewrites `RemoteAddr` for a request whose peer is in one of them to the rightmost `X-Forwarded-For` hop that is not, so a gateway in front of a waypoint resolves to the client rather than to either. Rightmost because every hop appends, so only the ones this server's own proxies wrote are true; a client can put anything it likes on the left. Unset trusts nothing, and behind a gateway every request then comes from a gateway pod, so `/link` sees one network for everyone a pod serves and offers a television's code to any phone that happens to arrive through the same one; set it wherever there is a proxy in front. The chart's `trustedProxies` is the pod CIDR. `make e2e` trusts loopback, which is how `link.spec.js` puts each device on a network of its own with the header.

`auth.Authorization` carries the connection's `RemoteAddr` alongside what the client sent, because the strict handlers never see the `*http.Request` and `GetEndpointInfo` answers from the caller's address.

**No sign-in screen lists a username.** `GetPublicUsers` answers an empty list whatever the accounts' `IsHidden` says, because a list anyone can fetch unauthenticated is half of every credential on the box. `jellyfin-web` then opens straight on its typed-username form, with Quick Connect beside it. The Android TV app cannot be told to skip its account screen — `ServerFragment` always draws it, from the public list plus the accounts the TV itself remembers — so with nothing public it shows "Add account", and that opens `UserLoginFragment` on Quick Connect by default: one press from the code and its QR. Its splashscreen QR names the bare `/link`, which finds the code by the phone's network.

`ForgotPassword` answers `ContactAdmin` and `ForgotPasswordPin` refuses every pin, both without reading a request or touching the database. A pin is only as private as the channel that carries it, and the server has none — no mail, and the log and the pin file upstream writes are both read by whoever runs the box rather than by the account holder. Anything that issues a pin here hands account takeover to everyone who can read a shipped log. `gojellyfin resetpassword` is what `ContactAdmin` means: an operator with database access, reading the new password from stdin the way `adduser` does.

**Single sign-on is OpenID Connect, and it is off unless `OIDC_ISSUER_URL` is set.** `internal/sso` is the domain — discovery, the authorization code exchange with PKCE, id_token and nonce verification, and the claims — and `internal/server/sso` is the transport, `GET /sso/oidc/start` and `GET /sso/oidc/callback`, registered beside `GET /socket` because a browser redirect is not an operation in the spec. Discovery happens on the first sign-in and is cached on success only, so a server that starts while the provider is down serves and signs in once it is back. `PUBLISHED_SERVER_URL` is required with it, because the redirect URI is `<PUBLISHED_SERVER_URL>/sso/oidc/callback` and a guess from the request's `Host` is a guess an attacker controls. The chart's catch-all `/` rule already sends `/sso` to the API, so the route needed no new match.

**An identity is the issuer and the subject, never the username.** `users.SignInIdentity` looks the pair up in `user.oidc_issuer`/`oidc_subject`, unique together, so a renamed account at the provider is still the same account here. A first sign-in creates the user with no password — `PasswordHash` empty is what `HasPassword` already reads, and bcrypt refuses an empty hash, so the account cannot be signed into by password until an administrator sets one. A username a local account already holds is refused rather than claimed, because a provider that lets people pick their own username would otherwise hand over any local account by typing its name; `OIDC_LINK_EXISTING_USERS` lifts that for a provider whose usernames are trusted, and only for a local account no identity has claimed yet. `OIDC_ALLOWED_GROUP` refuses anyone outside it, and `OIDC_ADMIN_GROUP` sets `IsAdministrator` on every sign-in, so leaving the group takes administrator away at the next one. Claims missing from the id_token are read from userinfo, which is where some providers put `groups` by default.

**The token reaches `jellyfin-web` through `localStorage`, not through a redirect.** The callback mints a session the way `AuthenticateUserByName` does and answers a page whose script writes it into `jellyfin_credentials` — the key `jellyfin-apiclient`'s `Credentials` reads, merged into the entry whose `Id` is `config.ServerID` — and then replaces itself with `/web/`. The page is same-origin with the client and `no-store`, and the token never appears in a URL, a log line or a `Referer`. The device is `sso-` and a hash of the user and the `User-Agent`, because the client's own device id lives in its `localStorage` and the callback is a navigation that carries none; the hash keeps one browser's repeated sign-ins on one device row.

The flow's state, nonce and PKCE verifier ride in a `gojellyfin_oidc` cookie on `Path=/sso/oidc`, `HttpOnly`, `SameSite=Lax` and `Secure` when the published URL is https, rather than in a table or in memory, so any API replica can finish a sign-in another one started. Lax is what lets the provider's top-level redirect carry it back.

Handlers read `auth.UserID(ctx)`, `auth.SessionFrom(ctx)`, `auth.AuthorizationFrom(ctx)` and return `auth.ErrUnauthorized`; `middleware.TokenFrom` is the only thing left in the middleware package that handlers touch, and only because websocket and media URLs cannot send headers.

### Transcoding

Audio a client cannot direct play is encoded by ffmpeg **in the process serving the request**. There is no worker protocol and no pool: the pod that serves the stream is the pod that encodes it.

**A client is handed one source and one url, and neither is its choice.** `PlaybackInfo` answers with exactly one `MediaSourceInfo` — `SupportsDirectPlay` and `SupportsDirectStream` false, `SupportsTranscoding` true, and a `TranscodingUrl` this server generated — or with no sources at all and `ErrorCode: NoCompatibleStream`. One answer does not list the item's other files, and `dto.ItemDto` sends no `MediaSources` either, so the version picker in `jellyfin-web` has nothing to pick from: an item's 4K and 1080p copies are one answer, not two.

**A client chooses a title, never a file.** That is the standing decision (#642), and it is why `PlaybackInfo` ignores the `MediaSourceId` a client sends in its body or its query: which of an item's files is played is the server's to answer, and a picture the client cannot decode is the server's to refuse. Re-deriving it on every call is safe rather than lucky, because `items.MediaSources` orders by `created_at, path` and `SourceFor` sorts with `SortStableFunc` — a seek or a re-post after a playback error is answered with the same file the client is already playing. A stream url still names its source id and the handler serves that file, because this server wrote the url; that is an instruction coming home, not a choice being made.

**Which file that is belongs to `internal/items`.** `items.SourceFor(ctx, itemID, items.Capabilities)` is the whole question — of the files behind this item, which one, and what has to change about it — and `items.Plan` is the answer. It walks the files tallest first and returns the first whose plan can be served; there is no ranking, because a file's plan is already the least that has to change about it. That is Dean's ordering with none of the machinery: a 4K needing its audio converted is returned before a 1080p that plays untouched because the 4K is reached first, and a file needing a picture encode is passed over while any file plays without one. At one resolution `richer` decides, which is bitrate then size, so the cheaper plan does not win a tie.

**A picture encode is the last resort, and it is 1080p H.264.** Only when every file needs one does `SourceFor` take a file to encode, and then it takes the shortest file that still fills 1080p, or the tallest when none does: the output is capped at `transcode.MaxHeight` anyway, so a 4K decoded only to be shrunk is cpu spent on pixels nobody sees, while encoding a 720p rip when a 1080p one sits beside it throws the picture away. The target is `transcode.VideoCodec`, which is `h264` High at level 4.1, 8-bit 4:2:0, progressive, square pixels, SDR — every condition `jellyfin-web` writes for `h264` holds for it, which is why the plan does not re-check them against its own output. It goes into the first container a `DirectPlayProfile` naming `h264` declares, `mp4` standing in for one that cannot be written to a pipe, with the audio copied when that profile names the source's codec and converted when it does not. A client that names no `h264` at all has nothing an encode could make, so it is `ChangeRefused` and answered `NoCompatibleStream`. Nobody picks a quality and there is no bitrate ceiling: x264 runs at a constant quality (`-crf 21`, `veryfast`), and `MaxStreamingBitrate` stays unread (#580).

**A `MediaSourceInfo` says only what this server determined.** Six of its booleans used to be read off `media_source` columns that nothing ever wrote, so the client was handed a `.Default(...)` as though it were a finding — the same defect that made `supports_transcoding` arm an unbounded `PlaybackInfo` retry and a schema-default `SupportsDirectPlay` play an AC-3 MKV in silence. `IsRemote`, `IsInfiniteStream`, `RequiresOpening`, `RequiresClosing`, `RequiresLooping` and `SupportsProbing` are now written false in `mediaSourceDto` as statements about this server: every source is a file on its own disk, played once from beginning to end, with no live stream to open or probe. The seven columns behind them are gone from the schema, because a value the server does not determine must not have a column implying it does. #597 is the wider set that is declared and unwritten but read by nothing.

**A song is planned like a film, from the audio half of the same profile.** `capabilities` reads the client's `Audio` `DirectPlayProfiles` into `items.Capabilities.Audio` and the containers of its `Audio` `TranscodingProfiles` that are not `hls` into `AudioEncodes`, and `SourceFor` answers an `items.IsAudio` item with `soundPlan` rather than `plan`: the file as it is when a direct play profile takes its container and codec, otherwise an encode into the first transcoding container ffmpeg can write, then the first direct play container that can carry what ffmpeg writes into it, otherwise `ChangeRefused`. A client that declared no audio profile is handed the file, because a file is never refused for something nobody read. The answer is the same shape as a film's — `SupportsTranscoding` true and a `TranscodingUrl`, here under `/Audio/{id}/stream.<container>` — and of a song's files the first that plays untouched wins over one that needs an encode, the richest first.

`internal/server/mediainfo` does three things and nothing else: `capabilities` reads the posted `DeviceProfile` into `items.Capabilities`, `SourceFor` is called, and `mediaSourceDto`/`served`/`streamURL` translate the plan back. The domain cannot see `api`, so a device profile becomes a domain type at the boundary.

A client says what it decodes in two places and both are read. A `DirectPlayProfile` is a triple — container, video codec, audio codec — and the `CodecProfiles` beside it carry the conditions: Chrome names `h264` and then says it wants `SDR`, a `VideoProfile` it knows, a `VideoLevel` it can reach, and neither interlacing nor anamorphic pixels. Reading only the first was the AC-3 bug again in the picture, since an HDR remux passes the codec check and plays washed out with nothing to say so. Which of those fails decides the cost, and `items.Capabilities.plan` answers it in one pass: the file as it is, the container changed with both streams copied, the audio converted with the picture still copied, or the picture encoded (`ChangeVideo`, `ChangeVideoAudio`) — `Change.EncodesVideo` is what `SourceFor` uses to put those last.

**A condition is held as hard.** Every one jellyfin-web writes carries `IsRequired: false`, and the client never evaluates them itself, so what that flag means for direct play cannot be read off the bundle — upstream uses it to decide what a transcode must enforce, not what direct play may ignore. Only the three verbs the client writes for video are implemented (`EqualsAny`, `NotEquals`, `LessThanEqual`); an unread verb, an unread property and an unprobed value all pass, because a file is never refused for something nobody read. That works because `probe` now fills in `video_range_type`, `is_interlaced` and `is_anamorphic`, which the ent schema had carried unwritten since it was generated — a file whose transfer characteristic ffprobe does not report is left unknown rather than called SDR.

**The url is an instruction, not a hint.** It names the source id, the container and the audio codec the response will carry, and `stream.Serve` executes it: the source it names is the file served, the same container as that source means the file itself, a different one means ffmpeg, and the audio is copied when the url names the codec that source already carries. That last comparison is the one thing the handler works out for itself, because codec names alone cannot say copy from encode — you need both sides — and it is taken from the source the url named. Reading it from the item instead was the bug: `items.AudioCodec` used to query the item's first audio stream, so an item with two files compared the version being served against a codec belonging to the other one and re-encoded audio it was told to copy. `items.Container` and `items.AudioCodec` are pure functions on a source now, one copy of each rule shared by the domain that plans and the handler that executes.

**`/Audio/{id}/universal` plans rather than decides.** It is reached without a `PlaybackInfo` url, so the client's profile arrives in its own query string instead: each `container` entry is a `container|codec|codec` direct play profile and a `transcodingContainer` sent with any protocol but `hls` is the transcoding one. `universal` turns them into the same `items.Capabilities`, `SourceFor` answers, and the handler executes the plan exactly as `Serve` executes a url, so there is one decision for audio whichever route a client took.

Codec names alone cannot tell a copy from an encode — aac re-encoded to aac is still aac — so the tests fingerprint each stream with ffmpeg's md5 muxer and compare it against the source. A needless audio encode still plays, so nothing but the cpu would notice it.

**Codec names are compared as written, because both sides write them the same way.** `jellyfin-web` builds its `DirectPlayProfiles` out of `h264`, `hevc`, `mpeg2video`, `vc1`, `msmpeg4v2`, `vp8`, `vp9`, `av1`, `aac`, `mp3`, `ac3`, `eac3`, `mp2`, `pcm_s16le`, `pcm_s24le`, `truehd`, `aac_latm`, `opus`, `flac`, `alac` and `vorbis` — ffprobe's own spellings, which is what `internal/probe` stores verbatim. The one codec with two names in circulation is DTS, and the client sends `dca` and `dts` together rather than choosing. An alias table was written and thrown away: nothing in it would ever have fired, and a guessed alias is a new way to be wrong.

The decision lives in the url rather than on the session because the capability data only ever arrives on the `PlaybackInfo` body: `jellyfin-web` posts no `DeviceProfile` with `Sessions/Capabilities/Full` (#579).

Three things have to agree and are tested together: the suffix in the url, the `container` parameter, and the `Content-Type` of the response. A browser dispatches on the header, which is how an AC-3 rip played its picture in silence.

**A url naming `videoCodec` is an encode, and one that does not is a copy.** The picture cannot be compared like the audio is, because a 10-bit or HDR `h264` and the 8-bit SDR `h264` a browser decodes share a codec name: the copy-or-encode question is answered by the plan, and the url carries the answer. `PlaybackInfo` writes `videoCodec=h264` and `maxHeight=1080` only for a plan that encodes, and `stream.Serve` encodes when it sees one, clamping a `maxHeight` above the ceiling down to it. `allowVideoStreamCopy` stays `false` on every url regardless, because that is what stops `jellyfin-web` retrying a playback error forever, not a statement about the picture.

The same-container shortcut in `stream.Serve` applies only when the url asks for nothing the file lacks: no `videoCodec`, and an `audioCodec` that is the source's own. An HDR `h264` mp4 asked for as `stream.mp4` is an encode into the container it already is, and an AC-3 mp4 asked for as `stream.mp4?audioCodec=aac` is a remux into it, and serving the file in either case hands back the very stream the plan refused. `copyTimestamps` follows the same test, because only the file served whole runs on its own clock.

An HDR source is tone mapped to SDR with `zscale` and `tonemap=hable` when `items.HDRTransfer` names a transfer, which is every probed range but `SDR`, `DOVIWithSDR` and unknown. The transfer, `bt2020` primaries and matrix are stamped onto the frames with `setparams` before `zscale` reads them, because the probe can call a file HDR while its frames carry a primaries or matrix tag `zscale` cannot find, and `zscale` answers a missing one with `no path between colorspaces` rather than a guess. A Dolby Vision profile 5 file has no HDR10 base layer for `zscale` to read and comes out with the wrong colours; that is a libplacebo filter, which neither the Alpine nor the Ubuntu ffmpeg carries. `bwdif=mode=send_frame:deint=interlaced` runs on every encode and only touches frames flagged interlaced, one frame out per frame in, since the default field mode doubles 1080i30 to 60. The picture is stretched to square pixels by its sample aspect ratio before it is bounded, so an anamorphic 720x576 PAL frame comes out 1024x576 rather than squeezed to 5:4. `-fpsmax 30` holds the frame rate under what level 4.1 allows at 1080p, which a declared `-level` does not do by itself, and `-force_key_frames` puts a keyframe every two seconds so the fragmented mp4 has a fragment to hand over that often.

`UserPolicy.EnableVideoPlaybackTranscoding` is answered false even though the picture can now be encoded: that policy is what `jellyfin-web` reads to decide whether to offer a bitrate menu, the server rather than the user chooses the quality, and `MaxStreamingBitrate` is not honoured, so the menu would change nothing (#580).

**Seeking is by position rather than by byte.** The client believes `PlayMethod: Transcode`, so a seek it cannot satisfy from what it has buffered re-posts `PlaybackInfo` with `StartTimeTicks` and follows the url that comes back, and ticks map straight onto ffmpeg's `-ss`. A source served untouched is a file, so `http.ServeContent` answers byte ranges and the client seeks in place instead. A remux copies the picture, so it starts at the keyframe at or before the position asked for.

Two things in `jellyfin-web` 10.10 decide whether that works, and both cost a broken seek to find. Before it follows the new url, `changeStreamToUrl` calls `DELETE /Videos/ActiveEncodings` and continues only if that succeeds; the path went with HLS from the v12 spec, so it 404ed and every seek on a remux was silently dropped. It is registered beside the stream routes and answers 204, because there is nothing to stop: an encode ends with the request that started it, and the client abandons that request when it changes the url. And a progressive transcode url without `copyTimestamps=true` makes the client add the start position to the element's clock, while it still seeks the element to that position with `#t=`. A remux starts its output at zero, so that is right for it; a file served whole already runs on its own clock, so the url for an untouched plan carries `copyTimestamps=true` or a resume at 2:00 plays from 2:00 and shows 4:00, and every seek after it lands twice as far as the bar says.

Which pods those are is a **routing decision**, not a protocol. The chart's `httproute.yaml` sends `/Videos` and `/Audio` to the streaming Service and everything else to the API's, and both deployments are the same image running the same `server` subcommand. A longer path prefix outranks a shorter one, so the split needs no ordering between the two routes.

That deletes the whole of what used to sit between them — the address list, the token, the round robin, the second subcommand and the HTTP hop that carried an encode from one pod to another. It also halves the bytes moved inside the cluster: a transcode used to cross the network twice, worker to API and API to client, and now crosses once.

`TRANSCODER_JOBS` bounds concurrent encodes on a pod and should not exceed its cpu limit, because one encode saturates about a core and a pod that accepts more than it can run makes every stream on it slower without finishing any sooner. A picture encode is the exception, so it takes `transcode.VideoSlots` slots — three, or every slot a pod with fewer has — and x264 is pinned to that many threads with `-threads`. Left alone it spreads across every core the node has, so one slot each let a pod full of them run every one slower than real time without ever answering 503. Three is what a 1080p `veryfast` encode measured at: about 2.5 cores of user time per second of wall, and a 1080p24 source at six times real time on three threads against twice on one, which leaves room for the tone map and a 4K decode in front of it. A pod with fewer slots than that still takes one picture encode at a time rather than refusing them all. Above that the pod answers 503 with a `Retry-After`, and **that refusal is the whole of the load balancing**: the gateway retries against another pod, with no pool, no load query and no shared state. `ErrNotAvailable` is the different answer — ffmpeg missing is not temporary, so it reaches the client as the 415 that says the device cannot play this.

The output is one progressive HTTP response rather than HLS, and that is what keeps the design small: a transcode is a single request from start to finish, so no second request has to find the same ffmpeg process, and nothing breaks with a second replica. HLS is what would force that question; the v12 spec carries no HLS path at all.

A client that goes away cancels the request context, which kills ffmpeg. A client that merely stalls blocks it on a full pipe instead, so a slow reader costs no CPU rather than racing ahead into a buffer. A client that vanishes *without* closing is the one case cancellation cannot reach: the write blocks rather than failing, and `TRANSCODER_STALL_TIMEOUT` bounds that to 30 seconds. What it must not kill is a client that is merely slow, and the two are told apart by where the relay is waiting — a slow client still takes a buffer's worth every so often, so the timer is reset by a read that moved something rather than by the pipe being full. Killing is both a cancel, which reaps ffmpeg, and a write deadline, which is the only thing that ends a write already blocked on a peer that stopped acknowledging.

ffmpeg answers a source it cannot read by exiting rather than by writing a short file, so `start` holds its return until the first byte of output arrives. A failure therefore reaches the handler as an error it can still answer 415 to, instead of as an empty stream the client believes.

After the first byte the status is spent, so a failure there is told by how the body ends. A progressive response carries no `Content-Length`, which leaves the chunked terminator as the only thing separating a finished encode from one that died: `process.Read` waits for ffmpeg at end of output and answers its exit status in place of `io.EOF`, and `relay` answers any relay or exit error by panicking with `http.ErrAbortHandler`, which drops the connection without the terminator (an `RST_STREAM` on HTTP/2) and logs nothing further. The client reads `unexpected EOF` instead of a track that simply ended, and `jellyfin-web`'s answer to a playback error is to re-post `PlaybackInfo` at the position it reached, which is the resume. The server does not resume itself, because a byte count maps back to a timestamp for CBR mp3 and for nothing else (#480). A pod killed mid-stream drops the connection the same way.

Only containers ffmpeg can write to a non-seekable pipe are in the table, which rules out plain mp4; ogg is out for the second reason that it wants libvorbis, which not every ffmpeg build carries.

The tests run real ffmpeg and ffprobe what comes back, so CI installs ffmpeg and a green run means bytes a player can decode.

### Current state

Users, sessions, devices, libraries, items and their user data are real rows, as are playlists, their entries and their shares; most other handlers still return hardcoded data or a 501. Audio transcodes when a client cannot take the source, and a picture no file can hand over untouched is encoded to 1080p H.264.

Live TV has no tuner (#525), no guide ingest (#526) and no recordings or scheduling (#527), and it has no tables either. `tuner_host`, `timer`, `series_timer` and `listings_provider` were declared and never written or read, so they are dropped; a schema guessed ahead of the feature is one the feature has to be talked out of, and re-declaring four entities is forty lines whenever #525 starts. `chapter`, `trickplay`, `media_segment` and `media_attachment` went the same way and for the same reason — `mediainfo` already answers `MediaAttachments` with a literal empty slice. Live TV's read paths still answer an empty result rather than a 501, because a 501 makes the web client retry the section on a loop while an empty result is both true and renderable; every write path and every by-id lookup stays 501.

**A column nothing reads is worse than a table nothing writes**, because it looks like data. Thirty of `item`'s fifty-six columns were dropped on that test: five enums no writer ever set (`location_type`, `extra_type`, `video_type`, `iso_type`, `video_3d_format`), the picture columns ffprobe never filled (`aspect_ratio`, `width`, `height`), `container` and `probed_at` — which the item carried as copies of the media source's, so a two-file item recorded whichever was probed last — and eighteen the metadata editor wrote and no response ever carried (`custom_rating`, `air_time`, `display_order`, `air_days`, `preferred_metadata_*`, the `airs_*` trio and the rest). `person` kept only its name and `studio` lost its unwritten `provider_ids`.

The audit that finds them is mechanical: for each column, who writes it and who reads it. A column with a writer and no reader is the dangerous kind — `original_title` and `production_locations` were fetched from TMDB on every identify and stored where nothing would ever look. Five that were written and unserved earned their keep instead by being served: `official_rating`, `community_rating`, `status`, `end_date` and `taglines` are on `ItemDto` now.

Deleting a column is safe here in a way it would not be elsewhere, because nothing reads the database but this server: cut the field, regenerate, and the compiler names every reader. A grep would have missed that `mediainfo.go` reads the *source's* container while `item.container` was dead.

**A table nothing writes is not a head start.** It is carried by every regeneration and every migration, and it reads as a feature that exists. The rule is that a schema lands with the code that writes it.

**The server id is `SERVER_ID`, and it exists for one reason.** A client files the token it holds under the id `/System/Info/Public` answers, so a server that takes over a Jellyfin install's hostname has to answer with that install's id or every carried token goes unused and each client asks for a sign-in. `config.ServerID` is therefore a variable `config.Module` sets once from `env.Config` at start, defaulting to gojellyfin's own, rather than a value threaded through every DTO that names it. `env` refuses anything but the 32 lowercase hex characters `device.txt` holds.

**Moving a Jellyfin install over is a script, not a subcommand.** `scripts/jellyfinmigrate` is its own `main` in this module, run with `go run` from a checkout, so the SQLite driver it needs is linked into it and not into the server or the image. It is in the module rather than beside it so it writes through the generated store, which is what makes a schema change break its build rather than its run, and so `go test ./...` covers it. `migration.Read` turns either layout of Jellyfin's databases into one `Source`, `migration.Run` writes that in one transaction and rolls it back for `--dry-run`, and `Report` is everything it could not carry. A user is matched by id and refused on a name another account holds; a token and an api key are first write wins; watch state is merged by the rule the global-item migration used, so a second run is safe and picks up titles a scan has added since. The cutover steps are in `README.md`.

A fresh database has no way in through the API — `CreateUserByName` requires an administrator and nothing seeds one — so `gojellyfin adduser` creates the first one. It reads the password from stdin rather than a flag, which keeps it out of the shell history and the process list; that is a security property, not a convenience, so it stays true of any command that takes a password. One-off jobs that need the domain services rather than a running server belong beside it as another subcommand under `cmd/gojellyfin`.
